# ADR-0033: Vanilla Hermes as a git checkout in pikkumies/hermes, updated separately

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-16
- Status: Accepted. Supersedes ADR-0009 (pinned, checksum-verified release tarball).

## Context
The operator's request of 2026-10-16: "make sure we use vanilla hermes, which can be updated at all will and seaprately, places in pikkumies/hermes ... and make sure no shit to clean is left over from this if changes needed".

ADR-0009 built a stripped tarball of one pinned tag (no `tests/`, `website/`, `apps/`, no `.git`) into `include/hermes-<tag>/`, so `hermes update` refused and only a Pikkumies commit could move Hermes. That is the opposite of each part of the request: the tree was not vanilla, Hermes could not be updated at will, its version was tied to Pikkumies, and it lived elsewhere.

Facts this rests on, read in upstream source (shallow checkout at `e5eb6b36fe`, 2026-10-16) and checked in a throwaway HOME:
- `hermes update` needs a git checkout with an `origin` remote.
- From v0.22 a venv plus `pip install -e .` no longer works: every core dependency in `pyproject.toml` is gated `; python_version >= '3.14'` (46 lines; `requires-python = ">=3.11,<3.15"`), so on Python 3.13 pip installs the package with no dependencies and `hermes` dies on its first import (found in the first live check of this ADR, 2026-10-16). Upstream's supported bootstrap is its package manager: `scripts/install.sh` (`ensure_uv`, `bootstrap_python`, `bootstrap_pm`) and `setup-hermes.sh` stage the uv pinned in `pm/lock.json` (sha256-checked) into the store slot `<store>/uv-<version>-<target>/`, let that uv install a bootstrap Python of the pinned minor version, and run `<python> -m pm.cli install` in the checkout. pm then installs its own Python and the tools into the store, commits the dependency environment under `HERMES_HOME/installs/`, and writes the checkout's launcher `.hermes/bin/hermes` (`hermes_cli/venv_sync.py` `publish_launchers`).
- pm's store is `HERMES_RUNTIME_DIR` when set, else `HERMES_HOME/tools` when `HERMES_HOME` is outside `~/.hermes` (`pm/environments.py` `store_root`, `hermes_constants.py` `get_default_hermes_root`); its uv cache is `HERMES_HOME/cache/uv` (`pm/packages.py` `uv_cache_dir`). So one `HERMES_HOME` gives install, runtime and `hermes update` the same store.
- Both upstream scripts also publish launchers into `~/.local/bin` and append a PATH line to `~/.bashrc`, `~/.zshrc` or `~/.bash_profile` (`setup-hermes.sh:210-262`; `install.sh` `wire_shell_path`), and `install.sh` tries sudo for system packages, so neither is run. `setup-hermes.sh` is the developer setup: its default `--test-environment` prepares the test environment, and its own comment says installers call `pm.cli install` without it.
- For a checkout of the official repository the updater follows the **stable** channel by default (`hermes_cli/update_channel.py` `default_channel`, `_tracks_official_origin`) and only moves forward. A stable release is a tag matching `STABLE_TAG_RE` = `vX.Y.Z` with a major of at most three digits. The old date tags (`v2026.9.24`) do not match, and a plain version sort ranks `v2026.9.24` above `v0.22.2`, so the tag has to be chosen with upstream's own rule.
- A Python environment moved or renamed after it is built breaks: script shebangs and `pyvenv.cfg` keep the old absolute path, and pm's launchers name the checkout's absolute path. The tree is set up where it stays.
- The updater stashes untracked files in the checkout (`update_cmd_stash.py`), so markers and locks belong outside it.
- Its "another instance is running" check is Windows-only (`hermes_cli/update_cmd.py` `_is_windows()`, read in v2026.9.24); on Linux it updates under running sessions.
- An update may install `libatomic1` with sudo or as root (`pm/libatomic.py`, run from `pm/client.py`), with no prompt when there is no TTY.
- An update writes `hermes`, `hermes-acp` and `hermes-agent` launchers into `~/.local/bin` unless `cli.expose_on_path` is false (`hermes_cli/_launchers.py` `expose_cli`). A bare `hermes` there would run with Hermes' own defaults in `~/.hermes`, without the Pikkumies config (approvals, hooks, logins), and leaves files outside `pikkumies/`.
- After an update the in-tree launcher is `<checkout>/.hermes/bin/hermes`, written by `hermes_cli/venv_sync.py` (confirmed in the throwaway HOME).
- `security.allow_lazy_installs: false` (ADR-0021) only gates the optional tools (agent-browser, chromium, cua-driver). The tools an update always installs (`pm/client.py` `ensure_tools_for_sync`) were measured in the throwaway HOME: ripgrep 6 MB, npm 17 MB, uv 54 MB, node 223 MB, Python 3.14 395 MB, ffmpeg 438 MB (about 1.13 GB), plus the committed dependency environment of 385 MB, all under `HERMES_HOME` (`local/hermes/tools`, `local/hermes/installs`).

## Options Considered
- **Keep the pinned tarball (ADR-0009).** Reviewed, checksum-verified builds; contradicts the request.
- **Run the upstream installer.** Vanilla in the upstream sense, but edits shell files and tries sudo.
- **Clone `main`.** Unreleased code; the updater would then wait for the next release anyway.
- **Clone the newest stable release tag, venv and editable install inside it.** Tried first; fails from v0.22 (dependencies gated on Python 3.14, above).
- **Run `setup-hermes.sh` or `install.sh` as they are.** Upstream's own bootstrap, but both edit shell files and publish `~/.local/bin` launchers; `install.sh` tries sudo.
- **Clone the newest stable release tag and run the bootstrap steps of those scripts, without the launcher, shell-file and sudo steps; let Hermes' own updater move it.** Chosen.
- **A separate `pikkumies hermes-update` verb.** Not needed: `pikkumies run update` already sets `HERMES_HOME` and passes the arguments to Hermes.

## Decision
- **Install.** `HermesInstall::ensure()` lists the tags of `https://github.com/NousResearch/hermes-agent.git` and picks the newest one matching upstream's `STABLE_TAG_RE`. In the background (`HermesInstall::build()` in a fresh PHP process, under `include/.hermes-build.lock`, log `local/install.log`, inside `setpriv --no-new-privs` when it exists) it runs `git clone --depth 1 --branch <tag>` into `pikkumies/hermes`, then upstream's bootstrap the way `install.sh` and `setup-hermes.sh` do it: the uv pinned in the checkout's `pm/lock.json` for this machine is downloaded (upstream's mirror only on a network failure, as upstream), its sha256 checked before unpacking, and staged into `local/hermes/tools/uv-<version>-<target>/`; `uv python install --no-bin --no-registry <minor>` and `uv python find --managed-python <minor>` give the bootstrap Python; `<python> -m pm.cli install` runs in the checkout. Then `include/.hermes-ready` is written. Every step runs with `HERMES_HOME=local/hermes`, `UV_NO_CONFIG=1` (as upstream) and `HERMES_RUNTIME_DIR` removed, so the store is `local/hermes/tools` now and for every later run and update. Two additions keep uv's own files inside `pikkumies/`: `UV_PYTHON_INSTALL_DIR=local/hermes/bootstrap-python` (else `~/.local/share/uv/python`) and `UV_CACHE_DIR=local/hermes/cache/uv` (pm's own uv cache). Unless `hermes.lazyInstalls` is on, pm gets `--without agent-browser --without cua-driver`, upstream's `install.sh --skip-browser --skip-computer-use`; pm records the choice, so `hermes update` keeps those tools out too (`pm/defaults.py`). Nothing in the tree is changed or removed, and no system Python is needed: ADR-0014's standalone Python is no longer used.
- **Complete** means `pikkumies/hermes/.git` exists and `include/.hermes-ready` exists. The hermes command is the launcher pm writes, `pikkumies/hermes/.hermes/bin/hermes`; it runs pm's committed environment.
- **No tree is ever deleted.** An incomplete tree (a failed or interrupted build) is moved aside to `pikkumies/hermes.broken-<UTC time>` by `pikkumies install` and reported; it can hold the user's own stashed changes. `post-update` (the daily cron) builds only where no tree exists at all, and not on a root-capable host without setpriv (ADR-0025).
- **Separate updates.** `pikkumies update` and its daily cron never update Hermes. Hermes updates only when the user asks: `/update` in a session, or `pikkumies run update [args]`. The latter runs the updater under `setpriv --no-new-privs` (refused on a root-capable host without setpriv, the `CronTick::wrap` rule), refuses an origin that is not the official repository, and needs the Hermes lock alone.
- **The Hermes lock** (`local/hermes.lock`): every `pikkumies run` session and every cron tick holds it shared for as long as Hermes runs; `pikkumies run update` takes it exclusive without waiting and refuses while any session or job runs. This replaces the `/proc` scan of ADR-0009.
- **Checks before every start.** `local/hermes-verified.json` records the last commit that passed. When the checked-out commit differs (an update from either path, a hand edit), `run` and `cron-tick` first check that every config key `HermesConfig` writes is still in the installed source (`HermesInstall::CONFIG_FACTS`), and that `hermes hooks test pre_tool_call --for-tool terminal` with an `rm -rf` payload is blocked by the Pikkumies delete guard. A failure stops the start with the reason; a pass is recorded. `pikkumies run update` runs the same checks right after updating. This also covers `/update` inside a session, which bypasses `pikkumies run update`.
- **Generated config.** `cli.expose_on_path: false` (no launchers in `~/.local/bin`); `updates.check: false` stays (a check at session start is a call to GitHub the user did not ask for, AGENTS.md); `security.allow_lazy_installs: false` stays (ADR-0021).
- **Doctor** shows the tag or branch, short commit, `vanilla` or `local changes` (`git status --porcelain`), whether origin is the official repository, the config-key check, and any `~/.local/bin/hermes*` that runs this tree. It never fetches. Every git call runs with `--no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null`, because the agent can write the tree.
- **Tests** find the installed source through `HermesInstall::sourceDir()`; where Hermes is not installed (CI) those tests report `skip`, never `ok`. `tests/HermesInstallTest.php` covers install, completeness, the lock, the checks and the no-leftover rules hermetically (a local bare repository, a fake uv in a tarball pinned by sha256, a fake bootstrap Python and pm).
- **No migration code.** No install outside the development checkout existed (the repository is private and the installer held). A stray build from ADR-0009 (and its standalone Python, ADR-0014) is removed by hand, with no Hermes session running: `rm -rf ~/pikkumies/include/hermes-* ~/pikkumies/include/python-3.13.16 && rm -f ~/pikkumies/include/hermes`, then `pikkumies install`.

## Consequences
- Hermes is the unmodified upstream tree at the release the user chose to update to, and moves only when the user asks. Accounts nobody updates stay on their install-day release; security fixes arrive only through an update.
- Trust moves from a reviewed checksum to TLS, GitHub and upstream's release process (accepted by the operator's request). Upstream's package manager installs dependencies from its lock file, which pins transitive versions more tightly than ADR-0009's pip did.
- Disk: the checkout, plus the tools pm always installs (about 1.13 GB, measured above) and the committed dependency environment (385 MB) in `HERMES_HOME`, plus the bootstrap Python. The install downloads them, not only the first update.
- `run` and `cron-tick` also remove `HERMES_RUNTIME_DIR` from Hermes' environment, so an inherited value cannot point pm at another store.
- A later `hermes.lazyInstalls: true` does not undo the recorded decline; `pikkumies run pm install agent-browser` opts back in (pm's own rule).
- On a host without the system library libatomic1 (needed by upstream's Node), pm's attempt to install it with sudo is refused by `setpriv --no-new-privs` and the build stops with pm's error in `local/install.log` (not tested live); the server's administrator installs the package.
- A Hermes release that drops or renames a key we rely on, or breaks the delete guard, cannot start under Pikkumies until Pikkumies is changed; the user sees the reason. The key check is a text check: it catches removals and renames, not changed meanings; the hook test checks the guard's behaviour.
- `pikkumies run update` waits for nothing: it refuses while another session runs, and the user closes it.
- A moved-aside `hermes.broken-*` tree stays until the user removes it; `pikkumies install` names it.
- When a check fails after `/update` inside a session, the next start refuses; the user can still see the reason with `pikkumies doctor`.
- `/update` inside a session runs Hermes' updater without setpriv (the session itself is not wrapped). On a terminal its libatomic step asks for the sudo password, which the user can decline; `pikkumies run update` is the path that can never escalate.

## Live check (when HermesConfig or the update path changes, or doctor reports drift)
In a throwaway HOME (never the real `~/.hermes`): `pikkumies install` until `local/install.log` says ready; `pikkumies doctor`; `pikkumies run skills list`; `pikkumies run hooks test pre_tool_call --for-tool terminal` with a destructive command (blocked); `pikkumies run update --yes`; `pikkumies doctor` again; run a daily `pikkumies update` and confirm the tree survives; check `~/.local/bin` and the shell rc files are untouched and `~/.local/share/uv` and `~/.cache/uv` were not created, and the sizes of the tree, `local/hermes/tools`, `local/hermes/installs` and `local/hermes/bootstrap-python`.

## Addendum 2026-10-17: a preinstalled account builds the runtime later
The operator, 2026-10-17: "infact pikkumies should be preinstalled ..... in most cases that is, if enough ram." PMSS now runs the installer for each new account with at least 1000 MiB RAM (PMSS ADR 0090), with `PIKKUMIES_SKIP_HERMES=1`, so account creation clones Pikkumies and writes its config but starts no build. Accounts created together, as when a server's users move to a new one, would otherwise each start a 2 GB build at the same moment.

The runtime then builds the first time either of two things happens:
- The account's daily `pikkumies update` runs. Its post-update step already builds where no tree exists, and the time of day comes from the uid, so neighbouring accounts build minutes apart.
- The user runs `pikkumies`. A session with no runtime used to print "Hermes is not installed yet" and exit; it now starts the build (`HermesInstall::ensure`, with its quota check), says so, and exits. The user runs `pikkumies` again when `pikkumies doctor` shows it ready.

## Addendum 2026-10-17: an automatic build leaves 10% of the quota free
The preinstall also reaches accounts that already hold the customer's data, and on those nobody asked for the 2 GB build. The room check alone only required the build's own size free, so an account with 2.6 GB left would end with almost nothing, and its downloads would then stop at the quota. An unattended build (the daily update's post-update step) now also keeps `HermesInstall::UNATTENDED_RESERVE` (10%) of both the disk quota and the file quota free; when it cannot, it skips and says why. A build the user starts by running `pikkumies` or `pikkumies install` keeps the old check, because the user chose to spend that space. Test: `tests/QuotaFilesRoomTest.php`.
