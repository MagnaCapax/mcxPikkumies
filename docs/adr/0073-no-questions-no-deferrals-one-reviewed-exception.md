# ADR-0073: No questions and no deferred work; the one exception is reviewed first

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-19
- Status: Accepted; amended 2026-10-19 (approvals off, see the amendment at the end). Amends [ADR-0020](0020-deletes-need-the-users-approval.md) (approvals mode, and which deletes are asked), [ADR-0034](0034-containers-category.md) and [ADR-0035](0035-performance-diagnostics.md) (stopping the container daemon and load tests are no longer asked), [ADR-0047](0047-halt-guard.md) (the judge's questions, and its 2026-10-19 amendment where an offer after a how-to question ended the turn), [ADR-0063](0063-common-mistakes-list-changing-data-and-no-python-tools.md) ("when no backup is possible the agent says so and asks first": the review below decides instead), [ADR-0048](0048-fileops-check-recheck-and-file-list.md), [ADR-0049](0049-backup-remote-over-ssh.md), [ADR-0053](0053-email-category.md), [ADR-0054](0054-tool-hooks-and-local-hooks.md), [ADR-0059](0059-settings-tiers-free-asked-and-the-persons-own.md) and [ADR-0068](0068-ssh-connections-need-a-stated-intent-and-the-persons-allow-and-deny-lists.md) (their questions go through the review below), and [ADR-0062](0062-hermes-config-seeded-once-pins-in-hermes-managed-scope.md) (new managed pins). Keeps [ADR-0056](0056-feedback-what-pikkumies-sends-to-pulsed-media.md)'s confirmation before `/feedback` is sent.

## Context
The operator ruled on 2026-10-19 that the agent asks no questions and defers no work for confirmation; the only exception is a destructive change to something that cannot be replaced, and even then an adversarial review decides whether to go on. The first message of a fresh install had offered to build a profile and promised to ask before any external lookup, which is the agent's main job. Pikkumies is to be offered by default on every seedbox: near zero questions, finished tasks.

What was found (Hermes v0.22.2):
- **The welcome message.** On the first message of an install Hermes adds a note telling the agent to offer to build a profile and, before any external lookup, to get consent each time (`agent/onboarding.py` `profile_build_directive`). It is added whenever `onboarding.profile_build` is not `off`; Pikkumies did not set it. With `off`, Hermes adds only a one-line introduction note. `onboarding.run` starts a separate first-run onboarding chat in the desktop app.
- **Approvals.** Pikkumies pinned `approvals.mode: manual` (ADR-0020), so every command on Hermes' dangerous list asked the user, including restarts and container stops. Hermes' default, `smart`, has a second model judge such a command first: approve runs it, deny or unsure asks the user (`tools/approval.py`, `tools/approval_smart.py`). `off` would also approve every question a Pikkumies hook raises, and the unattended `approve` modes would approve them in one-shot and cron runs, so neither fits.
- **Hook questions.** A hook's `approve` answer goes straight to the user's prompt; Hermes' smart step never sees it. Pikkumies' guards asked about deletes, exposure, stopping the container daemon, load tests, scheduled scripts, backup sends, mail, writes to local hooks, file moves over existing files, settings changes and SSH hosts not on the allow list.
- **The clarify tool** is described to the agent as the way to "ask the user ... when you need a decision ... before proceeding".
- **The halt guard** counted "a choice between options" and "approval for something destructive or paid" as waiting on the user, so a turn that ended on a menu or a request for consent ended quietly, and it had no question for handing work back.

## Options Considered
- **Remove every question.** Leaves irreversible deletes and disclosures, including ones steered by text the agent read, with no check. Against the operator's own exception. Rejected.
- **`approvals.mode: off`.** Also approves every Pikkumies hook question, the feedback send included. Rejected.
- **Edit each guard to decide for itself.** Seven copies of one decision. Rejected for one policy step in the orchestrator.
- **Route hook questions into Hermes' smart step.** Hermes does not do that for hook answers. Rejected; Pikkumies runs its own review for its own questions and leaves Hermes' smart step for Hermes' list.
- **Force Hermes' tool-use guidance on for every model (`agent.tool_use_enforcement: true`).** Hermes already turns it on for the model families it measured; its one measurement outside them showed no significant effect. Not done until a run of the question suite shows an effect.

## Decision
- **First contact.** Managed pins `onboarding.profile_build: "off"` and `onboarding.run: false`. The first message gets Hermes' plain introduction note only.
- **Hermes' own command list.** Managed pin `approvals.mode: smart`, with `auxiliary.approval` set to the hooks' light model under the one named provider. A failed or unsure guardian asks, which is the old behaviour. The unattended modes stay at Hermes' default, deny.
- **No clarify.** The user's config is seeded with `agent.disabled_toolsets: ["clarify"]`, and a tool hook (`hooks/tools/clarify/decide-yourself/`) blocks a clarify call with a fixed message: decide from what was found and do the work; when only the user can give a fact, say in the answer exactly what is missing. The block is the rule; the seeded line keeps the tool out of the model's list on new installs.
- **One ask policy for hook questions** (`lib/AskPolicy.php`, `lib/AskReview.php`, applied by `hooks/orchestrator.php` before the answers are merged):
  - a question from the person's own local hooks, or the `/feedback` send question, is asked as before;
  - a load test or stopping the container daemon is never asked: neither loses or reveals anything;
  - every other question, and any question of a kind the policy does not know, goes to one review by the hooks' light model, which answers three fixed questions: did the user ask for exactly this (R1); could it, if it is a mistake, lose the user's data for good, reveal it beyond this account for good, or switch off a safety check (R2, "cannot tell" counts as yes; for a send, a mail or an exposure R2 is yes without asking the model, because nothing sent can be unsent); does it reach further than the request needs (R3);
  - the question reaches the user only when R2 is not "no" and the request does not cover it (R1 not "yes", or R3 not "no"). A missing answer, an unparsable reply, a timeout or a missing snapshot keeps the question.
  - R1 is judged only from text the user wrote or saw: their last few messages and the agent reply they answered, kept by the halt guard's snapshot hook as separate entries. Tool output never reaches the review, so a file or page cannot pose as the user's request; nor does the halt guard's own continue or wrap-up text, which arrives as a user turn (an exact prefix match on its fixed sentences, as in search-first). Entries are kept only for a person's own session (`platform` `cli` for the CLI and one-shot runs, `tui` or `desktop`: `hermes_cli/oneshot.py`, `tui_gateway/server.py` `_resolve_session_platform`). A messaging-gateway session keeps every reviewed question, as before. A scheduled run (`cron`), a delegated subagent (`subagent`) or anything else keeps none, because there the "user message" was written by an agent (or nobody is known to have written it), so every reviewed question is kept, and refused where nobody can answer, as before. (Hermes does not pass `parent_session_id` to shell hooks, so the platform is the signal.)
  - Reading "destructive beyond something replaceable" this way: data deleted with no copy is lost; data sent or exposed beyond the account cannot be taken back, which is also the privacy rule in AGENTS.md (nothing leaves unless the user asked); and a switched-off safety check removes the protection this exception exists for. Anything that can be undone or regenerated is not asked.
  - The review's time is part of the `pre_tool_call` hook's own timeout; a review that would not fit is skipped and the question is kept.
- **rm -rf** is no longer refused outright with "ask the user to run it themselves"; it is a delete like any other and goes through the review. Hermes' unconditional floor still refuses a recursive delete of `/`, `~` or `$HOME` and system folders; guard-destructive refuses the same home folder written as `/home/<name>`, which Hermes' list does not cover.
- **Refusals that stay** (formatting, raw device writes, partitioning, world-writable permissions, fork bombs, force pushes, a renamed or decoded command, reads of stored passwords and the AI key, starting another agent with its safety layers off) no longer tell the agent to hand the command to the user. The message says the command is refused, not asked, and tells the agent not to reach the same effect another way, to finish the rest of the task, and to say in one line what was refused and why. A nested-agent start is told to do the work in this session.
- **Load tests and stopping the container daemon** are not asked (above). `borg delete --cache-only` stays a delete pattern: the review clears it, because the cache is replaceable, and a pattern exception could miss a real delete written on the same line.
- **The snapshot is not the agent's to touch.** guard-destructive blocks any call that names `local/state/halt`.
- **The halt guard** (`lib/HaltJudge.php`): Q4 also covers asking the user to choose between options for the requested work and offering to do it instead of doing it; Q7 counts as waiting only a password or login the user types themselves, a fact only the user has, a step a Pikkumies tool or safety check refused or asked about, a step the user declined, or a yes to an unrequested change that cannot be undone (ADR-0047's clauses about requested work and polite requests stay); a new Q9 asks whether the answer offered to do or check something the user asked for or asked how to do, instead of doing it (an offer of extra, unrequested work is not caught), handed the user a step the agent could do or check itself, or said it should work while the evidence shows no check. Q9 continues the turn whether or not it was a request: a how-to question about this account is the request when the change can be undone, so "I can change your config, want me to?" is continued with "do it ... back up anything you change first". This reverses ADR-0047's 2026-10-19 reading of question-suite run 3 ("asking was right"): under the operator's words the offer was the deferral. What went wrong in that run, a hand restart around a tool's refusal, stays wrong: the continue message keeps the request as the bound and now says never to work around a refusal from a Pikkumies tool or safety check, and the doctrine says to restart through the tool. The wrap-up idea is a plain suggestion, not a question.
- **Kept, with the reason:** the `/feedback` send question. The operator asked for it on 2026-10-19 (ADR-0056 amendment), the later words name no change to it, and the send gives the transcript to a third party.

## Consequences
- Requested work runs without questions; the user is asked only before an irreversible delete or disclosure that the user's own words do not cover, or that reaches further than they asked.
- A delete or send steered by text the agent read still stops at a question: the user's own words do not ask for it. This is a safety prompt, not a security boundary (AGENTS.md): a path built at run time inside code is out of sight of every guard, the snapshot block included.
- One light-model call per call that raised a reviewed question; none for load tests, container daemon stops, local hooks or `/feedback`.
- One-shot and cron runs: a kept question is refused as before (nobody to ask), and a command on Hermes' list is refused, because Hermes' unattended branch runs before its smart step.
- With `halt.disabled` there is no snapshot, so R1 cannot see the request and the irreversible kinds are asked.
- In an agent started by an agent, the guards still turn a question into a block before the review sees it (ADR-0020 amendment 2026-10-18).
- The doctrine, skill and tool texts that tell the agent to ask first are rewritten separately; until they are, the halt guard pushes back on an ask for requested work.
- Not verified live: how a real light model answers R1-R3 and Q9. A question-suite run should include a requested delete (it should run), an unrequested irreversible delete (it should ask), a hand-back answer (it should be continued), a how-to question about an undoable change in this account (it should be made with a backup, not offered) and a question about how something works (it should end after the answer).

## Amendment 2026-10-19: approvals off; a kept question is a block until the user's yes

**Context.** Later the same day the operator reported that users were still interrupted by approval prompts when the agent ran commands, and repeated the ruling above: no questions, no deferred work, the one exception a destructive action on something that cannot be replaced, and that one only after a review. Under `approvals.mode: smart` Hermes still asked the person whenever its guardian denied a command or was unsure, and every hook question the review kept still went to Hermes' prompt.

What was found (Hermes v0.22.2):
- `approvals.mode` accepts `manual`, `smart` and `off` (`tools/approval_context.py` `_VALID_MODES`). Under `off`, `check_all_command_guards` and `_run_approval_gate` (`tools/approval.py`) approve without asking; the hardline floor, the sudo stdin guard and `approvals.deny` still block (`hermes_cli/approvals_test.py`).
- A hook's `approve` goes to `request_tool_approval`, which runs `_run_approval_gate` (`hermes_cli/plugins.py` `_resolve_block_from_details`). Under `off` every hook question is therefore approved with nobody asked, in cron and one-shot runs too, because the `off` check comes before the unattended branch. This is why `off` was rejected above; the decision below removes the reason instead of keeping the prompt.
- Prompts outside `approvals.mode`: `approvals.destructive_slash_confirm` (`/new`, `/clear`, `/reset`, `/undo`) and `approvals.mcp_reload_confirm` (`hermes_cli/config_defaults.py`, `cli_modal_mixin.py`, `cli_info_mixin.py`); `model.switch_context_confirm_tokens` (`hermes_cli/model_selection_guards.py`); `security.protected_instruction_files`, which asks before a `write_file` or `patch` of an agent instruction file (`AGENTS.md`, `SOUL.md` and the like) or a project `.hermes` file even under `--yolo` (`tools/file_tools_write_guards.py`); and `hermes update`, which asks about config migration and restoring local changes unless given `--yes` (`hermes_cli/subcommands/update.py`).

**Decision.**
- Managed pins (and the same lines in the seeded user file): `approvals.mode: "off"`, `approvals.destructive_slash_confirm: false`, `approvals.mcp_reload_confirm: false`, `model.switch_context_confirm_tokens: 0`, `security.protected_instruction_files: false`. `auxiliary.approval` is no longer written: the smart guardian runs only under `smart`. CONFIG_FACTS lists the new keys, and the `approvals.mode` fact now names `"off"`. `pikkumies run update` passes `--yes` to Hermes unless `--yes` or `-y` is already there.
- No `approve` leaves the orchestrator. `lib/AskPolicy.php` turns every question into a run or a block with one of two fixed PHP messages (no model text):
  - **The review keeps it** (R2 not "no", and the user's words do not cover it): `AskPolicy::BLOCK_CONFIRM`. The command was not run; the agent finishes the rest of the task, says in one line what it would destroy or send, and runs the same command again only after the user says yes in the chat. The re-run is reviewed again, and R1 now says that a plain yes counts when it answers an agent reply that named this action and these targets. The halt guard's Q7 already counts "a step a safety check refused or asked about" as waiting on the user.
  - **No yes can be checked**: no evidence (a messaging gateway, a scheduled run, a delegated subagent, `halt.disabled`, and now also an agent started by an agent, whose "user" messages that agent wrote), less than two seconds left for the review, or no answer from it (no light model, `hooks.llm.disabled`, a timeout, an unparsable reply). Only the kinds `delete`, `exposure`, `send` and `mail`, the feedback send and the person's own local hooks are blocked, with `AskPolicy::BLOCK_UNCHECKED`: the command was not run and a yes cannot be checked here, so the agent finishes the rest and says in one line what it would destroy or send, with the exact command for the user to run themselves. Every other kind runs: it destroys nothing that has no copy. A second message is used here, not the confirm message, because the user's yes could never clear the call and the agent would ask again and again.
  - **The feedback send and the person's own local hooks**, asked unreviewed before, are reviewed as a send: R2 is yes whatever the model says, so only R1 "yes" with R3 "no", the user's own explicit yes, clears them.
  - Load tests and stopping the container daemon still run. An error in the policy blocks every question. The orchestrator turns any `approve` that would still be printed into `BLOCK_UNCHECKED`.
- Two kinds added where a question already existed: fileops-check's "mv replaces an existing file" carries `kind: delete`, and config-change's shorter `sessions.retentionDays` (Hermes then deletes ended sessions) carries `kind: delete`, so both stay blocked where no yes can be checked.
- `security.protected_instruction_files`, one adversarial pass. For keeping the protection: it stops an agent steered by text it read from writing instructions into a project's `AGENTS.md` that later sessions load. Against: the terminal form of the same write was never covered by it (the Hermes file says that vector is separate); the write can be undone (checkpoints in the seeded config, and the earlier text is in the conversation); Pikkumies' own `SOUL.md` is rebuilt at every start and Hermes exempts its home; Pikkumies' hooks, notes and settings have their own checks through this policy; and a fixed block in its place would stop the instruction-file edits users ask for. Pinned off; no prompt and no block.
- Agent-facing texts follow: the safety doctrine's "one question" line, the hook SOP's description of `approve`, fileops-check's block message (say what it changes and run it again, not "tell the user"), and the search-first gate no longer lists asking the user as allowed meanwhile.

**Consequences.**
- Hermes shows no approval prompt for commands, hook questions, slash commands, MCP reloads, model switches, instruction-file writes or `pikkumies run update`.
- Requested work runs. A delete, send, mail or exposure the user's words do not cover stops with one line to the user and runs after their yes.
- In a messaging gateway session such a delete or send cannot be confirmed in the chat; the agent gives the command instead.
- In cron and one-shot runs Hermes' own dangerous-command list is no longer refused (`off` comes before the unattended deny); Pikkumies' guards still block deletes, sends, mail and exposure there, and the hardline floor still holds.
- Where no yes can be checked, an asked settings change, an SSH host not on the allow list, a scheduled script and a write to local hooks now run.
- `HookAnswers::mergeApproves` and the merged-question cap (`HookUnits::APPROVE_SHOWN`) are reached by no production path any more (a block wins every merge, and no approve is left otherwise); their tests call them directly. Removing them and the per-guard length checks is a separate change.
- `NestedAgent::approvalsOff()` still reads only `HERMES_YOLO_MODE`: under `--yolo` the feedback send keeps its stricter refusal (ADR-0056). Reading the pinned mode there too would refuse every send in every session.
- Tests: `tests/ApprovalsOffTest.php`; the orchestrator, merge, notes, local-hook and guard tests now expect the block or the run.
- Not verified live: the pins against a running Hermes, how a real light model answers R1 for a plain yes after a named action, and that agents follow `BLOCK_CONFIRM` and `BLOCK_UNCHECKED`. A question-suite run should include an unrequested delete (one line, then it runs after "yes"), the same in a messaging session (the command is given), and a feedback send with and without the user's yes.

## Amendment 2026-10-20: --yolo is the default run mode

**Context.** The operator, 2026-10-20: "I noticed --yolo potentially still isnt' the dewfault run mode, it should be the default run mode". The pinned `approvals.mode: "off"` already bypasses every gate `--yolo` bypasses (Hermes `tools/approval.py`: the bypass check reads `--yolo`, the session `/yolo` and `approvals.mode == "off"` alike), but the flag itself was never set, so a session neither ran nor showed as yolo. Two Pikkumies units still read `--yolo` as "nobody to ask": the send guard refused a feedback or ticket send under it and handed the command to the person, and the opt-in feedback question stayed silent.

**Decision.**
- `bin/pikkumies` sets `HERMES_YOLO_MODE=1` (what `--yolo` sets before Hermes loads) for the person's own session, at depth 0, on the plain and the one-shot path. It is not added for an agent started by an agent; that agent stays guarded as before (NestedAgent: no new yolo, questions become blocks).
- `lib/SendGuard.php`: `--yolo` no longer blocks a send; the review decides, as for any send. At depth 2 or more the send is not run, and the message no longer hands the command to the person.
- `FeedbackAsk`: the opt-in question no longer goes silent under `--yolo`.
- `NestedAgent::approvalsOff()` stays as a reader of the flag; no unit treats it as a reason to hand work back.

**Consequences.** Hermes shows the session as yolo, which matches what it does. There is no setting to turn it off: the approvals bypass is the pinned `approvals.mode`, and the flag adds nothing a person could switch back on. Tests: `tests/LaunchRoutingTest.php` (the launcher contract), and the feedback, ticket and bundle send tests.
