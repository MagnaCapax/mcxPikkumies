# ADR-0061: Memories, context, tool calls and code lines on the `pikkumies tmux` status line

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-19
- Status: Accepted. Adds to the tmux status line of [ADR-0040](0040-credits-line.md); adds the `post_api_request` event to the hook units of [ADR-0030](0030-hooks-as-units-run-by-one-orchestrator.md).

## Context
The request of 2026-10-19: the status line should also show how many memories there are ("Memories: "), the context size, code +/- and other fun stuff, and maybe a tool calls counter.

What was found:
- The only live line Pikkumies owns is the `status-right` of the `pikkumies` tmux session (ADR-0040). Hermes' own status bar takes no field from outside without Python or a patch (ADR-0040, [ADR-0033](0033-vanilla-hermes-git-checkout-updated-separately.md)). That bar already shows the context used out of the window, with a bar and a percent.
- Memories: the files `pikkumies doctor` counts (`MemoryMetrics::memoryFiles`). A save is named `YYYYMMDD-<slug>.md` with the UTC date (`Lessons::save`), so the files saved today are known from their names.
- Tool calls and code lines: `post_tool_call` fires after every tool call, delegated agents' included, with the result under `extra` (Hermes v0.22.2 `model_tools.py`; [ADR-0044](0044-every-shell-command-is-logged.md)). A `patch` result carries a unified `diff` (`tools/file_operations_common.py` `PatchResult`); a `write_file` call carries its `content`.
- Context: `post_api_request` fires after every model request. For a shell hook its fields are under `extra` (`agent/shell_hooks.py` `_payload_fields`): `usage.prompt_tokens`, `context_length` and `platform`, which is "subagent" for a delegated agent (`agent/turn_response_intake.py`, `tools/delegate_tool.py`). Shell hooks may use it (`hermes_cli/plugins.py` `VALID_HOOKS`).
- Which session to count for: a tmux status line has no Hermes session id, and delegated agents have their own. Each tmux pane has `TMUX_PANE` in its environment, and tmux 3.5a expands `#{pane_id}` inside a status-right `#()` to the active pane's id before the command runs (checked on a private tmux server: `%0`, then `%1` after selecting the second pane). Hermes passes its own environment to shell hooks unchanged in a single-profile run (`build_subprocess_env(scrub_secrets=is_multiplex_active())`, nothing strips `TMUX_PANE`); read in the source, not seen in a running Hermes.
- tmux cuts `status-right` from the left when the terminal is too narrow (checked: a 60-column client kept the end of the line and the clock).

## Options Considered
- **Hermes' state database for tool calls and tokens.** A schema Pikkumies does not own (the reason [ADR-0044](0044-every-shell-command-is-logged.md) logs commands itself), and `pdo_sqlite` is not on every host. Rejected.
- **Keying by Hermes session id.** The status line cannot know it, and delegated agents have their own ids. Rejected for the tmux pane.
- **Leaving the context to Hermes' own bar.** Narrows what was asked, while `post_api_request` gives it for one small process per model request. Rejected.
- **More counters (duration, disk, torrents).** Hermes' bar shows the duration; disk and torrent figures need process runs every minute; the credits line already covers spending. Not added.
- **Two observer hook units writing per-pane counters, a `status-line` subcommand reading them, ahead of the credits line in the existing status-right.** Chosen.

## Decision
- **Counters** (`lib/SessionCounters.php`): one file per pane, `local/state/session-counters/pane<N>.json` (directory 0700, file 0600), integers only: `since`, `tools`, `added`, `removed`, `ctx`, `ctxMax`. No paths, commands, content or session ids. A pane id is accepted only as tmux writes it (`%` and 1 to 6 digits, `\z`-anchored). Writes are a read-modify-write under `flock`, so parallel tool calls lose nothing.
- **Only a pane where an interactive `pikkumies` started is counted.** That start (a terminal session, the same place the credits banner is printed) zeroes its own pane's file and removes other panes' files untouched for 7 days. A hook in any other pane, or outside tmux, writes nothing. The counts mean "since `pikkumies` started in this pane"; `/new` inside Hermes does not reset them.
- **`hooks/trace/session-counters`** (`post_tool_call`, fails open, 2 s): one tool call, plus the `+`/`-` lines of a `patch` diff counted inside its hunks by the hunk header lengths (a file header never counts; a removed line starting with `--` does), or the lines of a `write_file`'s content as added. A failed call or a result that is not JSON (cut to size) counts the call only.
- **`hooks/trace/session-context`** (`post_api_request`, fails open, 2 s): `ctx` = `usage.prompt_tokens`, `ctxMax` = `context_length` of the main agent's last request; a delegated agent's request or one without usage changes nothing. `post_api_request` joins `HookUnits::EVENTS`; Hermes ignores what it prints, and the orchestrator prints nothing for it.
- **`pikkumies status-line --pane=<id>`**, an internal subcommand: `Memories: 42 +3 today · Ctx: 48.2k/1M 4% · Tools: 17 · Code: +120 -8`. The pane part only when the pane has counters, `Ctx` only once a request reported usage; numbers through `CreditsFormat::short` (rounded down), ` | ` instead of ` · ` without a UTF-8 locale. Plain text, no colours. Any failure prints nothing and exits 0, as the credits line does. The pane is given as `--pane=<id>`, one word starting with `-`: a bare `%3` after `status-line` would make the words a prompt under [ADR-0022](0022-pikkumies-is-the-one-command-prompt-routing-and-path-install.md)'s rule and start a paid session every minute.
- **tmux:** `status-right` is `#(<php> <bin> status-line --pane=#{pane_id}) #(<credits line --tmux>) %H:%M`, `status-right-length` 150 (was 90), on the `pikkumies` session only, never `-g`. `%` and `#` of the paths are doubled as before; `#{pane_id}` is added after the doubling so tmux fills it in. tmux cuts from the left, so on a narrow terminal the new segment goes first and the credits line and the clock stay.
- **Plain sessions:** the start prints `Memories: N +M today` once, after the credits banner.

## Consequences
- The `pikkumies` tmux session shows, for the pane in front, what the agent there has done, and the memories count for the account.
- Cost, measured on one host with PHP 8.4: about 25 ms more per tool call (one more unit process, paid outside tmux too, where it exits at once), a new orchestrator run and unit per model request (tens of ms against requests of seconds), and one launcher run of about 25 ms per minute for the status line. No network and no model call. Not measured on PHP 7.3 hosts.
- Tool calls and lines include delegated agents; the context is the main agent's only. Lines written by shell commands (`sed -i`, `cat >`) are not counted, and a `write_file` that replaced a file counts all its lines as added.
- `TMUX_PANE` reaching the hooks through Hermes is read in Hermes' source; the first real `pikkumies tmux` session confirms it. If a later Hermes scrubs it, the hooks write nothing and the counters stay at zero.
- The counters are display state on this machine, zeroed at every start and never sent anywhere, so they do not follow `privacy.perfLogging` (which keeps search words and save history, [ADR-0041](0041-memory-metrics-save-reminder-and-wide-search.md)).
- A local hook unit may now use `post_api_request` too ([ADR-0054](0054-tool-hooks-and-local-hooks.md)).
- Tests: `tests/SessionCountersTest.php` (pane ids, reset before counting, adds and sets, 40 parallel writers, permissions, prune, the rendered line), `tests/SessionCounterHooksTest.php` (diff lines by hand, payloads, `extra` fields, subagent requests, both units through the orchestrator with and without `TMUX_PANE`), `tests/StatusLineTest.php` (the tmux plan string, routing of `status-line`, bin's output in a throwaway tree, the reset before Hermes starts), `tests/CoreTest.php` (the generated hook entries).

## Amendment 2026-10-19: where the bars sit, and their colours
The request of 2026-10-19, paraphrased: the status line sits above the prompt and should sit below it, and its yellow on black is ugly; make it pretty.

What was found:
- The bar above the prompt is Hermes' own status bar, not the tmux line. Hermes' classic CLI, the one Pikkumies starts (`hermes_cli/main_tui_launch.py` `_resolve_use_tui`: classic unless `--tui`, `HERMES_TUI=1` or `display.interface: tui`), stacks its layout in a fixed order: status bar, rule, input, rule (`hermes_cli/cli_tui_mixin.py` `_build_tui_layout_children`, v0.22.2 lines 416-439). `display.statusbar` only shows or hides it (`hermes_cli/cli_terminal_input.py` `_status_bar_visible_from_display_config`). The order changes only through a Python subclass of Hermes' CLI or a change to Hermes; this repository has neither ([ADR-0033](0033-vanilla-hermes-git-checkout-updated-separately.md), [ADR-0040](0040-credits-line.md)). Seen in a run of v0.22.2 in a private tmux server: the bar is drawn above the input.
- Hermes' other interface, the Ink TUI, can put its bar below the input (`display.tui_statusbar: bottom`, `ui-tui/src/components/appLayout.tsx` `StatusRulePane`). In a git checkout, as Pikkumies installs Hermes, the TUI is built with npm at its first start (`main_tui_launch.py` lines 197-219), and every prompt Pikkumies has measured (approvals, the halt guard, ADR-0054's 350 characters) was measured in the classic CLI. Read in source, not run.
- The yellow on black is Hermes' default skin: gold `#FFD700` on `#1a1a2e` (`hermes_cli/skin_engine.py`, `_BUILTIN_SKINS["default"]`). On a 256-colour terminal that background becomes xterm 234, the near-black of most dark terminals, so the gold text floats on the screen with no visible bar. Hermes reads a skin by name from `<HERMES_HOME>/skins/<name>.yaml` and merges its colours over the default skin (`load_skin`, `_build_skin_config`); `display.skin` picks it, and `/skin` writes that key to the user's file.
- Hermes' classic CLI sends 256-colour codes on Linux whatever `TERM`, `PROMPT_TOOLKIT_COLOR_DEPTH` or `NO_COLOR` say: it builds its own prompt_toolkit output without a colour depth (`hermes_cli/cli_terminal_input.py` `_build_cpr_disabled_output`), which skips the only place prompt_toolkit reads those variables (`prompt_toolkit/output/defaults.py` `create_output`). Seen in the same run: `NO_COLOR=1` and `TERM=linux` still gave `48;5;236`.
- On a light terminal Hermes passes every skin colour through a light-mode table (`hermes_cli/cli_render.py` `_LIGHT_MODE_REMAP`), the status bar's text too, while the bar keeps its own background; a colour in that table would turn dark on the dark bar.
- The tmux status line of the `pikkumies` session is already at the bottom unless the person's tmux.conf says `status-position top`; `pikkumies tmux` never set it.

Options considered:
- **Switch to the TUI for its bottom bar.** A first-start npm build on every account and a second, unmeasured interface for every prompt. Rejected here.
- **Hide Hermes' bar.** Loses the model, context bar and duration it shows, and plain sessions have no other live line. Rejected.
- **Ship a Python wrapper or patch Hermes to move the bar.** Against ADR-0033 and the no-Python rule. Rejected; the change belongs upstream: a `display.statusbar: bottom` in the classic CLI, as the TUI already has.
- **A skin for Hermes' bar, the same colours on the tmux line, and the tmux line pinned to the bottom.** Chosen.

Colours: 23 candidate schemes (four Hermes built-in skins among them) and Hermes' default were scored on WCAG contrast of each text colour on the bar at 24-bit and at the 256-colour value terminals get, on how calm they are (low chroma of the bar and of the everyday colours), on how they reduce to 16 colours (prompt_toolkit's nearest-colour rule) and on whether the bar shows as a band on black and on common dark theme backgrounds. Tinted near-blacks (Hermes' default, Tokyo Night, Nord, Catppuccin, Solarized) reduce to blue or lose contrast at 256 colours; near-black bars vanish on `#1e1e1e`; every Hermes built-in skin has a status colour in Hermes' light-mode table or a bar that vanishes on `#1e1e1e`. An adversarial round dropped the first pick, a `#303030` bar: it nearly vanishes on `#282828`, `#282a36` and `#282c34` themes (1.06 to 1.12:1) and its red missed AA. A theme-neutral bar (the terminal's own colours, no band) is readable everywhere but is not the colour scheme asked for; it stays the fallback. Chosen, `lib/StatusTheme.php`: a `#3a3a3a` graphite bar (xterm 237; 1.23 to 1.85:1 against those backgrounds and black), text `#dadada` (8.1:1), accent `#87d7ff` (7.2:1), dim `#b2b2b2` (5.4:1), levels `#87d787` (6.6:1), `#ffd75f` (8.2:1), `#ffaf5f` (6.3:1), `#ff8787` (4.9:1). Rendered only on a synthetic dark and a white terminal; the operator's own theme is not known. Every colour is an exact xterm-256 entry, so 24-bit and 256-colour terminals show the same, and none is in Hermes' light-mode table.

Decision:
- **Skin.** Every start writes `local/hermes/skins/pikkumies.yaml` (beside the user's config, before it is seeded): Hermes' status bar keys and the voice bar's background only, so the banner and the rest keep Hermes' look. The seed of the user's config selects it (`display.skin: "pikkumies"`). An install from before gets it once, through `hermes config set display.skin pikkumies` (backed up and logged as `skin-pikkumies`, [ADR-0062](0062-hermes-config-seeded-once-pins-in-hermes-managed-scope.md)), and only when its file names no skin; any `skin:` key there is the person's choice and stays. The marker `local/state/hermes-skin.json` makes it once, so a later `/skin default` is never undone. Not pinned: a managed `display.skin` would refuse `/skin`. `display.skin` joins `HermesInstall::CONFIG_FACTS`.
- **tmux.** With its status command, `pikkumies tmux` also sets `status-position bottom` and `status-style bg=colour237,fg=colour253` on the `pikkumies` session (never `-g`). The credits bar is `#[fg=colour114]`, `colour221` from 10 to 25% and `colour210` under 10%, over that bar; ADR-0040's black background behind the bar, there because tmux's default bar is green, is gone. `colourN` names, which every tmux version reads.
- **NO_COLOR.** When set at `pikkumies tmux`, no `status-style`, and the credits command tmux runs gets `NO_COLOR=1`, so `credits line --tmux` prints no colour codes. Hermes' own bar keeps its colours until Hermes reads `NO_COLOR` (above).

Consequences:
- Hermes' bar is a graphite band with light text in every Pikkumies session, and the tmux line matches it at the bottom. Hermes' bar stays above the input until Hermes offers a bottom position; when it does, Pikkumies can set it in the seed.
- One more key Pikkumies edits once in the user's file, and one more config fact, so a Hermes that stops reading `display.skin` is refused like any other.
- Not verified on a live host: `hermes config set display.skin pikkumies` on a real install (the same command path as [ADR-0072](0072-hermes-shared-metrics-answer-recorded-as-no-thanks-in-the-users-file.md)'s repair), and the look on a light terminal. Rendered locally in tmux 3.5a with Hermes v0.22.2: the skin's colours reach the bar as `48;5;237` / `38;5;253` / `38;5;117`, and every tmux option above is accepted.
- Tests: `tests/StatusThemeTest.php` (exact xterm entries, contrast, light-mode table, the skin file, the seed and the managed file, the once-only selection and a chosen skin left alone, the tmux steps with and without colour, the credits bar colours and NO_COLOR, bin's wiring); `tests/CreditsLineFormatTest.php`, `tests/CreditsLineTest.php` and `tests/StatusLineTest.php` follow the new codes and steps.
