# ADR-0086: A local-only telemetry history for diagnostics and health runs

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-20
- Status: Accepted. Amended 2026-10-20 after a security review (report row F9): name checks used `$` instead of `\z` (a trailing newline passed); the per-source lock used a blocking `flock`, which could stall the tool recording rides along with; nothing bounded a single source's growth, so a remote `serve` peer calling an allowed verb such as a torrent client's `stats` repeatedly could grow telemetry faster than any local run would. Fixed: `\z` in both name regexes; the lock is `LOCK_EX|LOCK_NB` with a short, bounded retry, never a blocking wait; and one limit applies to every caller alike -- at most one write per source per minute and at most 1 MiB per source-day file, both counted as a drop (not a failure) in `list`. "Kept forever by default" (the Decision below) is unchanged: these are growth-rate and per-file caps, not retention.

## Context
The operator's request, verbatim: "when the doctor and diagnostics are run, we should always store locally that telemetry, a bit like we do for the hdds etc. so they can be fetched later on, accompanying a log file or sqlite which collects the various times a measurement was taken so charts etc. can be produced."

Facts read for this decision:
- PHP 7.3 on a PMSS host may not have `pdo_sqlite` built; a hard sqlite dependency would make the feature silently unavailable on exactly the hosts it is meant to help. No new runtime dependency is allowed (AGENTS.md).
- [ADR-0035](0035-performance-diagnostics.md) already keeps its own history (`local/performance/runs.jsonl`, written by `performance check --tick` on a scheduled job) for a different, narrower purpose (per-hour medians of its own probes) and is not touched by this ADR; the two histories stay separate because they are written by different code on different schedules and nothing requires unifying them now (YAGNI).
- [ADR-0041](0041-memory-metrics-save-reminder-and-wide-search.md) already solved the adjacent problem -- a local-only, never-sent history of a measurement, gated by a setting -- for memory-search metrics: monthly JSON Lines under `local/state/<name>/`, directory 0700, files 0600, gated by `privacy.perfLogging` (default on).
- `privacy.telemetry` also exists (`Config::defaults()`, `pikkumies/lib/Config.php:41`), but every place that defines it (AGENTS.md, [ADR-0032](0032-settings-configure-skill-first-run-and-install-flags.md), `pikkumies/lib/Launch.php:218`, `pikkumies/tools/system/pikkumies-configure/ConfigureSettings.php:15`) says the same thing: it is reserved for a future external *sender* and today gates nothing, because no sender exists. ADR-0032's own amendment, when ADR-0041 built the first local logger, confirms the split in writing: "a logger now exists [ADR-0041] ... `privacy.telemetry` is still a setting only: nothing is sent." Gating a local-only history behind `privacy.telemetry` would read as a promise ("telemetry is on") about something this feature never does (send data), and would collide with the setting's documented, repeated meaning the moment a real sender is eventually built behind it.

## Options Considered
- **A sqlite file.** Rejected outright by the operator's own "no sqlite dependency" framing and by `pdo_sqlite` not being guaranteed present; kept as a documented later option (any future exporter can read the JSON Lines files written here and build a `.sqlite` from them without changing this format).
- **Reuse `MetricsLog` (ADR-0041) directly**, one monthly file per *kind*. Rejected: that class's own retention and scrub machinery is shaped for ADR-0041's two fixed kinds (`searches`, `saves`); this feature needs an open set of *sources* (one per tool that records) each keeping its own small numeric fields, and a chart wants fine-grained recent buckets more often than a monthly grain gives cheaply. A new, smaller class next to the tool it serves follows the same proven pattern (lock file, atomic append, 0700/0600) without forcing an unrelated shape onto it.
- **Gate it behind `privacy.telemetry`.** Rejected for the reason in Context: that setting's one stable meaning across the whole codebase is "nothing is sent, because no sender exists"; this feature never sends anything either, but reusing that flag's name for a *different* promise (local storage) would make a future real sender's on/off switch retroactively ambiguous about data that was never sent in the first place.
- **One JSON Lines file per source per UTC day, under `local/state/telemetry/<source>/YYYYMMDD.jsonl`, gated by `privacy.perfLogging`, kept forever by default (chosen).** Mirrors ADR-0041's proven shape (lock file, atomic append through a temporary file is not needed here since every write is a pure append, 0700/0600 permissions) for a different, open-ended set of sources; per-day files make `series`'s bucketed read cheap (glob a day-string range, read each file once) and make `prune --keep-days N` a plain file delete, no rewrite.

## Decision
- **New tool unit**, `pikkumies/tools/system/telemetry/` (`TelemetryLog.php` the storage class, `telemetry.php` the CLI): verbs `record <source> --json <object>` (internal; appends one record), `series <source> <field> [--days N] [--bucket hour|day]` (one record per bucket: `ts`, `value` the mean, `min`, `max`, `count`), `list` (sources on disk: days, bytes, oldest/newest, failures), `prune [--keep-days N]` (deletes nothing without `--keep-days`; named `prune` so the delete guard asks first, AGENTS.md).
- **Record shape**: `{"ts": <unix time>, <field>: <number>, ...}`, at most 32 fields, field names letters/digits/underscore starting with a letter, values numeric or boolean (cast to 1/0) only -- no free text, no names, no identifiers. A bad value or name is dropped silently (the caller is a diagnostic tool recording what it has, not a user to scold); only a bad *source* name throws, because every call site here names its own source as a fixed string and a bad one is this ADR's own bug, not a runtime condition.
- **Gate: `privacy.perfLogging`** (default on), read fresh from `Config::load()` on every call, exactly as ADR-0041's `DocSources::appendMetric` does. Off: `record` writes nothing and reports `written: false`, never an error. `privacy.telemetry` is never read by this tool.
- **Never breaks the tool it rides along with.** Each of the four call sites wraps its `TelemetryLog::record(...)` call in `try { ... } catch (Throwable $e) { TelemetryLog::noteFailure($source); }`; `noteFailure` itself never throws. None of the four call sites' own return value changes: the record a verb already returned to its caller is computed first, telemetry is recorded from it as a side effect, and the same record is returned unchanged.
- **Wiring** (one shared place per the builder's own ownership split): `system-status account` and `system-status health` (sources `system-account`, `system-health`); the storage unit's `stats` verb (source `storage`); every torrent client's `stats` verb, through the one shared closure in `tools/torrent-clients/lib/Torrents.php` (source `torrent-<client>`, the client class's own name lower-cased, so a fourth or fifth client unit gets its own source for free without this file changing again). Fields recorded for each source are in `USAGE.md`'s table.
- **Retention**: kept forever by default (the operator's own words); `prune --keep-days N` is the one way to delete, and it deletes across every source at once -- there is no per-source retention setting, because YAGNI and because the operator asked for "they can be fetched later on", not for automatic deletion.
- **Remote exposure**: the `services` forced command (a different builder's unit, `tools/seedbox/services/serve.php`) whitelists only `system/telemetry {series,list}` -- a peer that was given a service account can read its history, never write a record or prune one.

## Consequences
- A chart of quota, memory, traffic or torrent counts over a week or a month can be built from `series` without a database, on every PMSS host whether or not `pdo_sqlite` is present.
- `privacy.telemetry` stays exactly as documented everywhere else in the codebase -- a setting with no effect yet -- and nothing in this ADR changes its meaning or starts gating anything behind it; a future ADR that builds a real sender still owns that decision on its own terms.
- Four small, well-understood files (`system-status.php`, `storage.php`, `Torrents.php`, plus this tool's own two) carry the only places a record is produced; a fifth source needs one more such call site, not a change to `TelemetryLog.php`.
- Follow-up outside this unit, left to whoever wants it later: a `--human` chart renderer for `series` (bars, as `pikkumies-configure`'s `stats` tables already do); a sqlite exporter reading these same JSON Lines files.
