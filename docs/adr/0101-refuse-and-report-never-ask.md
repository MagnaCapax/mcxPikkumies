# ADR-0101: Refuse and report, never ask; scheduled jobs and gateway chats get the same review

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-20
- Status: Accepted; amended 2026-10-20 (the key guard and the system-unit privacy rule, at the end). Amends [ADR-0073](0073-no-questions-no-deferrals-one-reviewed-exception.md) (the two block messages, R1, which sessions give evidence, the halt guard's Q7) and [ADR-0020](0020-deletes-need-the-users-approval.md) (what happens in scheduled and unattended runs, and the nested-agent message).

## Context
The operator ruled on 2026-10-19: "no asking questions, no work deferrals to confirm none of that shit -- only exception is _destructive_ actions beyond something which is replaceable, but even then adversarial review round to see if should continue". On 2026-10-20 the operator read the public description of what Pikkumies does ("It asks you first before it deletes files, ... In a scheduled job nobody is there to answer, so those actions are refused, unless you once answered "always" for that exact command.") and called it "an antipattern of harassing the operator if still true. needs to be removed, just an adversarial double check for such actiosn", and asked for the other antipatterns like it to be found and removed.

What was found in the code before this change:
- After ADR-0073's amendment no question reached Hermes, but the ask policy's two block messages still handed the step to the person: `BLOCK_CONFIRM` told the agent to run the command again "only after they say yes in the chat", and `BLOCK_UNCHECKED` told it to give the user "the exact command, so they can run it themselves". The halt guard's Q7 counted "a step a safety check refused or asked the user about" as waiting on the user, so such a hand-back ended the turn quietly.
- R1 asked whether the user asked for "exactly this action", so requested work that was not worded exactly ("clean up the old downloads") was refused.
- A scheduled job and a messaging-gateway chat gave the review no evidence, so every delete, send, mail and exposure there was refused whatever the person had asked for. The "always" answer the public text mentions no longer exists (approvals are off, ADR-0073 amendment).
- About ninety agent-facing sentences in doctrine, skills, USAGE files, READMEs and tool hints still told the agent to ask first, to wait for a yes, or to hand the user a command.

What was checked in Hermes (v0.22.2, the newest stable tag, which Pikkumies installs: `HermesInstall::STABLE_TAG_RE`; the same names in v0.21.5):
- A scheduled job's agent is built with `platform="cron"` (`cron/scheduler.py:2496`) and runs `agent.run_conversation(prompt)` (`:1977`). The prompt is built by `_build_job_prompt` (`cron/scheduler_prompt.py:283`): the job's own `prompt` (`:297`), a `## Run Context` block appended for a per-run prompt or data (`:299`, `:305`), data blocks and the job notepad put before it, each ending in a blank line, and the fixed cron hint first (`_CRON_HINT`, ending in a blank line). So the job's prompt is part of the turn's `user_message` at `pre_llm_call`, never all of it.
- `pre_llm_call` passes `platform` and `sender_id` (`agent/turn_context.py:818`, `:820`); shell hooks get every keyword other than the top-level ones under `extra` (`agent/shell_hooks.py:93`).
- `cronjob_manage` (`tools/cronjob_tools.py:1057`) takes `action` (`create`, `update`, ...) and `prompt` (`:1080`).
- The gateway admits a sender (`gateway/authz_mixin.py:629` `_principal_authorized`) when a platform allow-all variable is set (`:652`), through a role, a pairing approval, a group chat id, an explicit allowlist (`<P>_ALLOWED_USERS`, `GATEWAY_ALLOWED_USERS`; names in `gateway/pairing.py:67`), and with no allowlist when `GATEWAY_ALLOW_ALL_USERS` is set (`:676`). Bots skip the person allowlist on four platforms (`authz_mixin.py:38`); four platforms have their own open dm/group policy (`gateway/run.py:2219`). A group thread is shared by default (`gateway/config.py:580`, `thread_sessions_per_user: False`). Shell hooks inherit the gateway's environment in a single-profile run; under profile multiplexing it is scrubbed (`agent/shell_hooks.py:341`).

## Options Considered
- **Ask the person, as before.** The operator's words rule it out.
- **Run every irreversible step without a check.** Against the operator's own exception: a delete steered by text the agent read would run.
- **Treat the cron prompt as the person's words.** The agent writes the prompt; a job could then clear anything it names. Rejected; the person's words are recorded when the job is made instead.
- **Give every gateway chat evidence.** A gateway that lets anyone (or any bot) write would let a stranger's message clear a delete. Rejected; only an explicit allowlist with the sender on it counts.

## Decision
- **One refusal, reported, never asked.** `AskPolicy::BLOCK_REFUSED` with two fixed reasons (`WHY_UNCOVERED`: what the user asked for in their own messages does not cover it; `WHY_UNCHECKED`: the check could not run in this session). The message tells the agent not to reach the same effect another way, to finish the rest, to list the step as skipped with the reason in the final answer, and not to offer to run it or give the user the command. The orchestrator turns any leftover `approve` into the unchecked refusal. The hook log gets the counts and a reason code (`unchecked`), never the person's words.
- **R1 is about coverage.** "Is this action, on these targets, covered by what the user asked for in their own messages shown, as part of doing what they asked?" A plain yes to an agent reply that named the action still counts. R2 and R3 are unchanged; a send, a mail and an exposure still force R2 to yes.
- **The /feedback and /ticket sends and the person's own local hooks** are still reviewed as a send (R2 forced yes): the user's own request for the send clears them; no special yes is needed and none is asked for.
- **Scheduled jobs.** When the agent calls `cronjob_manage` `create` or `update` with a prompt in a session that has the person's words, guard-destructive asks the review whether the person asked for this scheduled job (`lib/CronAuth.php`, R1 yes and R3 no). Only then it records `{sha256 of the prompt: the prompt, the person's asked entries, the time}` in `local/state/ask/jobs.json` (dir 0700, file 0600, temp name and rename under a lock, at most 200 entries, newest kept). The call itself is never blocked by this. In a run with platform `cron`, the halt snapshot finds a recorded prompt in the turn's `user_message` where Hermes puts it (after a blank line or at the start, before the end or a `## Run Context` block) and uses the recorded entries as the evidence; the review still judges every action against those words, so the prompt itself is never evidence. guard-destructive blocks every call that names `local/state/ask`, as it does `local/state/halt`. The hook log gets `cron-auth` `hit`/`miss` and `cron-auth-record` reason codes only.
- **Gateway chats** (`lib/GatewayAccess.php`) give evidence only when the platform is one of Hermes' built-in messaging platforms; no allow-all (`GATEWAY_ALLOW_ALL_USERS`, `<P>_ALLOW_ALL_USERS`) or bot admission (`<P>_ALLOW_BOTS`) is set; no dm or group policy is `open` (the platform's variables, or anywhere in the user's or the managed `config.yaml`; a config file that cannot be read counts as open); an explicit list (`<P>_ALLOWED_USERS` or `GATEWAY_ALLOWED_USERS`) is set without `*`; and the turn's `sender_id` is on it exactly. A sender let in another way (pairing, a group chat id, a role, an alias) gives none. The evidence is then only the current message and the agent reply it answers, because a shared thread's earlier messages may be other people's. Anything unknown means no evidence.
- **The nested-agent block** in guard-destructive, config-change and ssh-connect no longer says "Tell the user the command": the step is skipped and reported.
- **The guards' other hand-backs**: publish-check tells the agent to take a secret out itself and publish again, and publishing it anyway is the send review; SendGuard, config-change's `configure undo` block and the SSH deny and strict-mode blocks report instead of handing the command over; the merged-question cap no longer suggests the user change a check.
- **The halt guard's Q7** counts "a step a Pikkumies tool or safety check refused" as waiting, no longer "or asked the user about".
- **Agent-facing text.** `doctrine/safety.md` gets one section, Irreversible actions, with the rule above and the short list of what stays the person's own: logins they type in their own terminal, consent for data leaving (their own request, or `ticket.auto`), terms, their own settings (`ssh.allow`, `ssh.deny`, `ssh.blockUnknown`, web search), money, facts only they have, and a host key that does not match. Every skill, USAGE, README, SOP and tool hint that told the agent to ask, to wait for a yes or to hand a command over is deleted, pointed at that section, or, for those reserved items, reworded to say what is missing in the answer. `--expect` counts, a person's own `--yes` and the hard refusals stay. `tests/NoAskTextTest.php` keeps the phrasings from coming back.

## Consequences
- Requested work runs; an irreversible step the person's words do not cover is skipped and named in the answer, with the reason, and nothing waits for a reply.
- A scheduled job made from the person's request can prune, delete or send what that request covers. A job made without the person's words (by an agent started by an agent, from a tool output, before this change) still has its irreversible steps refused; re-creating it from the person's request records it.
- A gateway chat on an explicit allowlist works like a terminal session for the review; an open gateway does not.
- One light-model call per `cronjob_manage` create or update with a prompt.
- The record is a safety record at the same trust level as the halt snapshot, not a security boundary (AGENTS.md): the agent's user owns the file, and a path built at run time is out of every guard's sight.
- Not verified live: how a real light model answers the coverage R1 and the job question, and the gateway rule against a running gateway. A question-suite run should include a requested and an unrequested delete in a session, the same in a job made from the person's request and in one made without it, and a delete from an allowlisted and from an open gateway.
- Tests: `tests/AskPolicyTest.php`, `tests/ApprovalsOffTest.php`, `tests/AskPolicyOrchestratorTest.php`, `tests/NoQuestionsGuardTest.php`, `tests/CronAuthTest.php`, `tests/GatewayAccessTest.php`, `tests/NoAskTextTest.php`.

## Amendment 2026-10-20: the AI key files, the key mask and system units' status

**Context.** A check of the public "what it will and will not do" claims found three gaps behind "it never reads your AI key" and "it does not look at other accounts' connections". guard-destructive refused a command that named a key file, but not one that globbed it (`cat ~/.v*Key`), reached it by a relative path (`cd ~/pikkumies/local/hermes-managed && cat .env`) or swept it up in a content search from the home folder (`grep -rh ^key= ~`). The media apps' logins already had that treatment (GuardMediaCreds, [ADR-0078](0078-changing-the-login-of-the-users-own-apps.md)). `Provider::mask` still showed the first and last four characters of a long key. And a system unit's `systemctl status ssh` is answered by PID 1 as root, past /proc's `hidepid=2`, so it lists other accounts' process titles (`sshd: USER@pts/N`); so does `systemctl show -p ControlGroup|MainPID` and the D-Bus `GetUnitProcesses` call (`systemd-cgls` reads /proc and does not). Several texts still told the user to edit the platform key file by hand, though the platform writes `~/.virsilipasKey` itself ([ADR-0004](0004-provider-key-and-root-detection.md) amendment 2026-10-17).

**Decision.**
- `GuardKeyFiles.php` (beside `GuardMediaCreds.php`, whose word, path and home-search helpers it reuses) refuses a call when a word resolves to `~/.virsilipasKey`, `~/.pikkumiesKey` or the Hermes `.env` in `local/hermes/` or `local/hermes-managed/` (also through the `~/pikkumies` link), with `~`, `$HOME`, `/./` and `dir/../` folded and a relative path read against the last `cd` or the call's working folder; when a glob would expand to one (shell dot-file rules); and when it searches content from the home folder itself, unless its exclude options cover every key file name. The name rule in `$secretPatterns` stays.
- `Provider::mask` shows eight stars for every key.
- The guard's privacy block also refuses a system unit's `systemctl status`, a `systemctl show` without `-p` or of `ControlGroup`, `MainPID`, `ExecMainPID` or `ControlPID`, and `GetUnitProcesses`, with the same message that names no path. `systemctl --user ...`, `is-active`, `is-enabled`, a manager property (`show -p DefaultTimeoutStopUSec`), root's own use (euid 0) and a command through `sudo` or `doas` (which work only where the account has root) stay allowed. The server-admin skill reads unit status with `sudo`.
- The install guide, the installer's last line, the credits hint and the guard's key message say that on Pulsed Media the key file is put in place for the user, and that for their own provider the user writes `~/.pikkumiesKey`.

**Consequences.**
- A content search from the home folder that excluded only the media logins is now refused too; it must exclude the key files as well, or search a subfolder.
- Out of sight, as before: a name built in a variable or in code, and a program that reads files by itself. A safety prompt, not security (AGENTS.md).
- Tests: `tests/KeyGuardTest.php`, `tests/HookGuardMediaCredentialsTest.php`, `tests/ProviderKeyFileModeTest.php`, `tests/HookGuardDiskTest.php`.

## Amendment 2026-10-20: the records are guarded by path, not only by name
A CWE review of the scheduled-job record found that guard-destructive's name rule (`state/ask`, `state/halt` in the command text) missed a relative write from inside the folder (the payload's cwd), a `cd` by glob and a glob path, so the agent could forge a record and with it the evidence for a scheduled job. `GuardKeyFiles::checkStateDirs` now refuses those three ways for both folders, with the key guard's own path resolution. A path built in a variable or by a program stays out of sight: the records remain a safety record, not a security boundary.
