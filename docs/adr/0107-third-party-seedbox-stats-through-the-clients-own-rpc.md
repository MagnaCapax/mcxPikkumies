# ADR-0107: Third-party seedbox stats through the client's own RPC, never a Pikkumies serve

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-21
- Status: Proposed. Amends [ADR-0084](0084-services-list-and-moving-torrents-between-boxes.md) (its Third parties clause: a tunnel key "port forwards to the client's API only" was not true of the key line, and a public HTTPS client RPC is now read directly) and [ADR-0085](0085-encrypted-secret-store.md) (an optional host pin per secret). Builds on [ADR-0101](0101-refuse-and-report-never-ask.md) (refuse and report, never ask, never hand the user a command of the agent's own).

## Context
The request of 2026-10-20: statistics of every seedbox on the services list "just like they were local", other remote management that might be needed, for boxes of our own and for accounts at other providers (Feral, Bytesized, Whatbox and the like).

What main had: `transport: tunnel` existed for a box without Pikkumies (key line `restrict,port-forwarding,command="/bin/false"`), but `ServicesRemote::run` refused every service whose transport was not `pikkumies` ("no Pikkumies serve there"). A third-party box could be added to the list and nothing on it could be read.

What the providers publish (read 2026-10-21):
- autobrr's shared-seedbox page (autobrr.com, Configuration, Download clients, Shared seedbox providers) lists rTorrent for Feral as `https://SERVERNAME.feralhosting.com/USERNAME/rtorrent/rpc`, TLS, basic auth, username `rutorrent`; for Whatbox as `https://<hostname>.whatbox.ca/xmlrpc` or `https://rtorrent.<yourdomain>.box.ca/xmlrpc`, basic auth with the account's user; for Bytesized as `https://<username>.<hostname>.bysh.me/rutorrent/plugins/httprpc/action.php` (ruTorrent's httprpc plugin, not rTorrent's XML-RPC).
- Whatbox's wiki page "Using XMLRPC with Python" gives protocol HTTPS, host `server.whatbox.ca`, port 443, mountpoint `/xmlrpc`, the account's user, and an example URL with `user:password@` inside it.
- Bytesized's API page: a read-only API at `https://bytesized-hosting.com/api/v1/` with `api_key` as a parameter; `accounts.json` returns, per account, bandwidth and disk use, `paid_till`, `server_name`, the pretty quota strings, and also `login_password`.
- None of these pages documents a management call (restart, reinstall) or a rate limit.

Reusable code: `RtorrentXmlRpc` (`tools/torrent-clients/rtorrent/XmlRpc.php`) encodes and decodes rTorrent's XML-RPC independently of the transport; only `RtorrentScgi` (a local socket) used it. `lib/Http.php` is the one HTTP client (TLS verified, redirects off, a local port only when this account owns it). `Services::fanout` already runs several services at once with a per-call timeout.

## Options Considered
- **Treat `tunnel` like `pikkumies` and call straight through.** Rejected: there is no serve on the other end to enforce ADR-0084's whitelist, data roots or delete gate.
- **An SSH tunnel to every third-party box, as the transport's name suggests.** Rejected as the default: Feral's and Whatbox's rTorrent RPC is already public HTTPS with basic auth; a tunnel adds an SSH hop and a key for no gain. Kept as a later step for a box whose client listens only locally (a NAS, a VPS).
- **A shell transport running `du`, `df` and the client's CLI over SSH.** Rejected: a shell key is the whole account, which ADR-0084 reserves for `transport shell` on the user's explicit request.
- **One RPC adapter per wire protocol, reusing the codec, behind the same client class; read verbs only.** Chosen.
- **Pin a secret to its host only.** Simplest, and it stops an edited record from sending the login to another machine. Not enough alone: Feral's documented RPC form is `https://SERVERNAME.feralhosting.com/USERNAME/rtorrent/rpc`, one shared web front with a path per customer, so an edited URL path on the pinned host would hand the Basic header to a co-tenant's path. Kept as the weaker form for a host with one account behind it.
- **Pin the host and a path prefix.** The user types `--host server.feralhosting.com/user/`; the request URL must be under that prefix on a `/` boundary. Same "changes only with a new value" property, and it closes the co-tenant path. Chosen, alongside the host-only form.

## Decision
- **Read verbs for `transport: tunnel`, in this process.** `services remote` runs `torrent-clients/rtorrent` `list`, `show` (with `--trackers`), `stats` and `traffic` for a tunnel service here, against that box's rTorrent RPC from `clients.rtorrent`: `url` (the provider's https address), `user` (the basic-auth login name; the service's `user` when absent) and `auth` (`secret:<handle>`). The records are `RtorrentClient`'s own, so they read exactly like a local box's, with `service`. Not through `Torrents::run`: its `stats` adds this machine's quota and writes this machine's telemetry series, and `show --files` reads this machine's disk; a tunnel's `stats` is the client's figures only, and `show --files` is refused with that reason.
- **Changes are refused for a tunnel service, before anything is recorded or sent.** `add pause resume recheck repath remove`: "no management API at a box without Pikkumies; the provider's own panel or the user's own SSH session does this". Every other unit and verb (qBittorrent, Deluge, find, telemetry, system-status show and health) is refused with what a tunnel answers. ADR-0101: reported as not done, never turned into an ssh command of the agent's own. `transport shell` stays refused as before; a changing verb to it is now refused before its intent is recorded.
- **One adapter per wire protocol.** `RtorrentHttpRpc` (`tools/torrent-clients/rtorrent/HttpRpc.php`) has `RtorrentScgi`'s shape (`address`, `call`) and POSTs the same XML-RPC body through `Http::request` (reply cap `RtorrentScgi::MAX`), with `Authorization: Basic` built from `user` and the secret, read from the store at each request. `RtorrentClient` takes it as an optional transport; with none, the local SCGI path is unchanged. qBittorrent (WebUI API), Deluge (JSON-RPC) and Bytesized's httprpc get sibling adapters later.
- **Refused before any request:** a URL that is not `https` (`Http.php` itself allows http), that carries `user:...@` (the form Whatbox's page shows), whose port is not 443, or that is not a plain host and path; a URL path with an empty, `.` or `..` segment or %-encoding (curl would squash dot segments and reach another path than the one checked); a URL host that is not the service's own `host` (both by `SshLists::host`), or one the person's SSH lists refuse (`Services::refuseListed`); a secret whose pin does not allow that host and path. A reply that holds a NUL byte (UTF-16 and the like, which would hide a DOCTYPE from the codec's check) or does not begin with `<?xml` or `<methodResponse` is refused, a remote reply is parsed without `LIBXML_PARSEHUGE`, and a remote fault text is cut at 300 characters; the local SCGI path keeps its parse as before. No error, record or log line carries the secret, the header or a URL's userinfo; provider error text is scrubbed of the secret and its encoded forms. Whatbox's `rtorrent.<yourdomain>.box.ca` form names another host than the box, so it is refused; the `<hostname>.whatbox.ca` form is the one that works.
- **The pin (amends ADR-0085).** `secrets set <handle> --host <pin>` and `secrets rotate <handle> --host <pin>` store a pin with the value inside the encrypted store: `host` (any path on that host) or `host/path/prefix/` (only URLs under that prefix, on a `/` boundary). The host is normalised by `SshLists::host`; the path takes plain characters only, with no empty, `.` or `..` segment and no %-encoding, and gets a trailing `/`. `Secrets::pin($handle)` returns `{host, path}`, null when unpinned, and `Secrets::pinAllows()` compares a request against it; no other verb writes it, `rotate` without `--host` keeps it, and `rotate --host <host>` without a path drops an old prefix. Honest boundary, inside ADR-0085's own: the pin scopes the tool path. A process running as the user with the store unlocked can decrypt the vault and write a new pin itself (ADR-0085, Consequences), so the pin is not a wall against same-account code. What it does give: an edited service record (`clients.url` and `host`, which the agent writes with `services edit`) cannot make `remote` send a stored login to another host, or with a prefix pin to another path, because the pin changes only together with a new value. With a host-only pin, another path on the same host on port 443 (a co-tenant's path on a shared web front) is not separated; the docs recommend the prefix form for Feral-style per-user paths.
- **A pin refusal never names a re-pin to the record's address.** The record is agent-writable and the pin is what the user typed, so a mismatch refusal says that the service record now names another box or path than the pinned one, to check `services show`, and that a new pin is right only if the user moved the box themself, typing the address they know. It carries no `secrets rotate ... --host` command. An unpinned secret's hint shows the command with a placeholder, never a host read from the record. The services skill tells the agent never to supply a `--host` value from the record.
- **No secret-shaped field in the services list.** `Services::normalize` refuses, inside `clients`, any key whose name contains `pass`, `secret`, `token`, `key`, `cookie` or `auth` (`auth` itself excepted), an `auth` that is not `secret:<handle>` (`Secrets::HANDLE_RE`), a `url` with userinfo, a query or a fragment, and a `user` with a colon, space or control character, with the ADR-0085 hint: the user adds the secret in their own terminal with `secrets set <handle> --host <host>`. The refusal never echoes the value. This catches the shapes, not every secret: a value under an innocent-looking key (`login`, `pw`) cannot be told apart from a user name.
- **Bytesized: `account` only.** Bytesized's rTorrent is behind ruTorrent's httprpc plugin, which this adapter does not speak. For a tunnel service with provider `bytesized` and `account_auth: secret:<handle>` (`services add|edit --account-auth`), `remote <nick> system/system-status account` GETs `accounts.json` with `api_key` built at request time from a secret pinned to `bytesized-hosting.com`; one record per account with the documented fields, and `login_password` dropped. One key answers for all the user's Bytesized accounts, so a service keeps only the accounts whose `server_name` is a label of its host (`<user>.<server>.bysh.me`, autobrr's form); the SSH lists are checked for the service host and for `bytesized-hosting.com`, the host actually contacted. Any other provider refuses `account` ("no customer account API is published there"). The field is top-level, not in `clients`, because `find` and `move` treat every `clients` key as a torrent client.
- **The tunnel key is pinned to its endpoint (corrects ADR-0084).** ADR-0084 said the tunnel key reaches "the client's API only"; `restrict,port-forwarding` forwards anywhere. When the service's `clients` name a TCP endpoint (`endpoint` as `tcp://H:P` or `H:P`, or `port` for `127.0.0.1:P`), `setup` writes `permitopen="H:P"` for each into the key line. OpenSSH applies permitopen to TCP forwards, and once one is set it refuses that key's unix-socket forwards too (openssh-portable channels.c, `channel_permit_all` and `open_match`), so a service with any socket endpoint (a `socket` key, as in the Feral preset, or an `endpoint` that is a path), mixed or not, keeps the old line in v1: permitopen would silently remove its socket forward. A malformed TCP endpoint refuses setup rather than writing an unscoped key. The forward opener itself is a later step; nothing in v1 opens a tunnel.
- **rffmpeg is already covered.** Its remote host comes from the services list with a shell key and a GPU, which shared third-party seedboxes do not give; nothing changes for it.
- **Defense in depth, not a root-cause fix:** with no published rate limit, the existing `Services::fanout` cap (4 at once, 300 s) applies; a slow or failing provider is one error record for that service and never stops the others.

## Consequences
- `services remote feral1 torrent-clients/rtorrent stats` answers for a Feral or Whatbox box with the fields a local box gives (the `endpoint` field is the https address), or one error record: locked store, missing handle, unpinned or mismatched pin, not configured, timeout, HTTP error, non-XML reply.
- The user's flow: `secrets set feral1-rpc --host <server>.feralhosting.com/<user>/` in their own terminal, typing the address they know; `services edit feral1 --transport tunnel --clients '{"rtorrent":{"url":"https://<server>.feralhosting.com/<user>/rtorrent/rpc","user":"rutorrent","auth":"secret:feral1-rpc"}}'`; then `services remote feral1 torrent-clients/rtorrent stats`.
- Local `stats` also writes the doctor's telemetry series (ADR-0086); a tunnel's does not, because a remote client's figures under the local source would mix two boxes into one series. A per-service series needs a source keyed by service: a named follow-up.
- The open question these sources cannot settle: whether Feral offers SSH key login at all; the read path needs no SSH, so it matters only for a later tunnel or shell case there.
- An outbound HTTPS call to the provider's own domain, at the user's request for a box they added: the same privacy posture as `backup remote` ([ADR-0049](0049-backup-remote-over-ssh.md)) reaching one other machine.
- Follow-up: the tunnel `show` repeats the six lines of `Torrents::run`'s show (without `--files`); one shared helper when that code is next touched.
- Tests (run on a testing machine): `tests/RtorrentHttpRpcTest.php`, `tests/ServicesRemoteTunnelTest.php`, normalize, setup and `permitopen` cases in `tests/ServicesTest.php`, a pin case in `tests/SecretsTest.php`.
