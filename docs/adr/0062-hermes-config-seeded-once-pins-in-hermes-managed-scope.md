# ADR-0062: Hermes config is seeded once; Pikkumies' pins live in Hermes' managed scope

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-19
- Status: Accepted. Supersedes the [ADR-0003](0003-hermes-integration.md) consequence "Hand edits to generated Hermes files are overwritten"; amends [ADR-0005](0005-hermes-wiring-verified-against-source.md) (a late key reaches Hermes through the managed files), [ADR-0007](0007-customising-shipped-skills.md) (a hidden shipped skill is not generated), [ADR-0021](0021-web-access-off-unless-configured.md) (a web search backend configured in Hermes now stays), [ADR-0024](0024-hermes-features-on-at-install.md) (the feature defaults are seeded, not pinned) and [ADR-0033](0033-vanilla-hermes-git-checkout-updated-separately.md) (the start check also covers the managed scope). Amended by [ADR-0072](0072-hermes-shared-metrics-answer-recorded-as-no-thanks-in-the-users-file.md): Hermes reads the shared-metrics answer from the user's file only, so `telemetry.shared_metrics` is seeded and repaired there, and only its `send` stays pinned. Extended by [ADR-0074](0074-the-dashboard-needs-a-login-and-its-own-hermes-backend.md): the Hermes environment also sets `HERMES_GATEWAY_LOCK_DIR`.

## Context
The request of 2026-10-19: Hermes settings must persist, both the first configuration and the changes made with Hermes' own commands; "maybe the local override path ... or maybe only build it fully on first launch THEN only do careful edits with deterministic tools", and those tools must log and back up the configs.

Until now every `pikkumies` start rewrote `local/hermes/config.yaml` and `local/hermes/.env` in full (`HermesConfig::write`, called by `generate()` before every run). Hermes writes the same files: `hermes config set`, `/model --global`, `mcp add`, plugins, skills, fallback providers, memory, TTS and terminal setup. Keys shaped like `*_API_KEY` go to `.env`. So every change made in Hermes was gone at the next start, a web search backend and its key included (the path [ADR-0021](0021-web-access-off-unless-configured.md) documents). [ADR-0001](0001-layout-install-and-update.md) says updates never overwrite what the user or the agent changed; the rewrite broke that for Hermes.

The rewrite also did two jobs that must stay: a key or setting changed after install reaches Hermes ([ADR-0005](0005-hermes-wiring-verified-against-source.md)), and Hermes never starts without the safety hooks. It also put every privacy pin back at each start (approvals manual, no keyless web fallback, no borrowed logins). Once Hermes-side edits persist, a pin the agent flips would persist too, so the pins need another home.

Hermes v0.22.2 (the newest stable release, which `pikkumies install` checks out) has exactly two config layers: the user's `config.yaml` and a "managed scope" in `$HERMES_MANAGED_DIR` (or `/etc/hermes`), honoured when the variable is set and the directory exists (`hermes_cli/managed_scope.py` `get_managed_dir`). Managed values win per leaf (`apply_managed_overlay`), lists are replaced whole, `config set`/`unset` refuse a managed key ("managed by your administrator", `config.py` `_exit_if_key_managed`) and `save_config` drops managed keys from the user's file. A managed `.env` is applied last, with override (`env_loader.py` `_apply_managed_env`). There is no include or override file and no batch `config set`. Hermes also keeps its own copies of `config.yaml` on every load that parses (`HERMES_HOME/backups/config/`, five kept). The skills loader reads `skills.external_dirs` and `skills.disabled` from the user's file only (`agent/skill_utils.py`), not through the overlay. PHP here has no YAML parser.

## Options Considered
- **Every pin in the managed scope, the user's file left alone.** The skills loader would not see `skills.external_dirs`, so every Pikkumies skill would disappear; pinning `plugins.enabled` would refuse every other plugin.
- **A Pikkumies override file merged into a regenerated config.yaml.** Changes made inside Hermes are still lost at the next start.
- **Capture-back: diff the file against the last generated copy, or parse YAML in PHP.** No YAML parser; a subset parser breaks on what Hermes' writer produces.
- **Seed once, then put every pin back with `hermes config set` when the file changed.** About 25 Hermes processes after each edit, Hermes' config lock is in-process only (write races), and a flipped pin holds until the next start instead of being refused.
- **Pikkumies skills linked into Hermes' own skills directory.** Generate deletes files it did not write there (data loss for skills the agent makes), and Hermes' write guard for external skills is lost.
- **Managed scope for the pins, the user's file seeded once, the rare list edits through Hermes' own `config get/set`, backed up and logged.** Chosen.

## Decision
- **Two layers.** `local/hermes-managed/` is Hermes' managed scope. Pikkumies rebuilds it at every start, atomically: `config.yaml` with the pins and `.env` with `PIKKUMIES_API_KEY` (0600). If either write fails, `run` refuses to start, as before. `local/hermes/config.yaml` and `local/hermes/.env` (`HERMES_HOME`) belong to the user. Pikkumies writes `config.yaml` once, at the first start, with every setting (the operator's "build it fully on first launch"), and never writes `.env`.
- **Pinned** (managed, refused by `hermes config set`): `model.provider`, `model.default`, `providers.pikkumies.*`, `approvals.mode`, `web.keyless_fallback`, `web.keyless_rescue`, `auth.adopt_external_logins`, `security.allow_lazy_installs`, `updates.check`, `cli.expose_on_path`, `skills.guard_agent_created`, `hooks.<every event Pikkumies hooks>`, `hooks_auto_accept`, `sessions.auto_prune`, `sessions.retention_days`, `telemetry.shared_metrics`, `auxiliary.goal_judge`, and the key. They change through `local/config.php` and `pikkumies configure` under the [ADR-0059](0059-settings-tiers-free-asked-and-the-persons-own.md) tiers. One Hermes writer skips the refusal: `/model <m> --global` writes the user's file directly, and the managed value then wins without a message. `pikkumies -m` still picks the model for a session, because Hermes' CLI flag wins over the configured default.
- **Seeded, then the user's:** `skills.external_dirs`, `checkpoints.enabled`, `plugins.enabled`, `auxiliary.background_review.enabled`, `curator.enabled`, and everything Hermes writes.
- **`skills.disabled` by omission.** A shipped skill named in `skills.disabled` is not generated (its tool stays in `tools/INDEX.md`), so Pikkumies no longer writes Hermes' `skills.disabled`. A Hermes skill is hidden with Hermes' own command, which now persists.
- **Deterministic edits of the user's file** (`lib/HermesUserConfig.php`, recorded by `lib/HermesConfigBackup.php`) happen only in rare cases. Each one is backed up first to `local/backups/hermes/<file>.<UTC time>.<pid>` (0600, every copy kept) and logged as one line in `local/state/hermes-config.jsonl` (time, action, file, key, sha256 before and after, backup; never a value). The cases:
  - the generated skills directory is missing from `skills.external_dirs`: it is appended through `hermes config get`/`set`, which keeps the other entries and the file's comments. Without this, scheduled jobs would silently run without the Pikkumies skills;
  - the one-time move from the old layout: the old "this file is rewritten" header line is replaced, Pikkumies' own `PIKKUMIES_API_KEY` line leaves `.env`, and hidden shipped skills leave Hermes' `skills.disabled`. Every other byte stays. The marker `local/state/hermes-config.json` is written last. A step that needs Hermes waits until Hermes is built, and a second start changes nothing. If the old header shows up again (an older version ran), the move runs again.
  A failed edit is logged and noted on stderr, and the start goes on, because the pins and hooks are in the managed file. The next start tries again. Concurrent starts serialise on `local/hermes-config.lock`.
- **The environment.** Every Hermes Pikkumies starts (run, cron-tick, the feedback export, the start check, the edits above) gets `HermesConfig::env()`: `HERMES_HOME`, `HERMES_MANAGED_DIR`, and no `HERMES_RUNTIME_DIR`. `HERMES_MANAGED_DIR` joins the variables an agent may not change or unset ([ADR-0020](0020-deletes-need-the-users-approval.md) nested-agent rule). The key guard covers `hermes-managed/.env` as it covers `hermes/.env`.
- **Start check** ([ADR-0033](0033-vanilla-hermes-git-checkout-updated-separately.md)): `HermesInstall::LAYER_FACTS` must still be in a changed checkout (the `HERMES_MANAGED_DIR` override, the overlay, the managed `.env`, the refusal). `verify()` also runs `hermes config set approvals.mode manual` and requires the refusal. Hermes' "formatting error" for an unparseable user file is not a refusal, because that file is the user's to fix. The record of a passed check names what was checked, so an unchanged checkout is checked once more after the Pikkumies update that brings this change; a Hermes without the managed scope is then refused (`pikkumies run update` still works) rather than run without its hooks.
- **Rules for later changes.** A new default that must reach every install goes in the managed file or in a numbered migration step, never only in the seed (the seed reaches new installs only). A new pin needs its Hermes reader checked for the overlay: a reader of the raw user file (as the skills loader is) cannot be pinned, so the key goes in the seed and is repaired like `skills.external_dirs`.
- The managed scope is a guard rail against the model's mistakes, not security against the user ([AGENTS.md](../../AGENTS.md)): the user runs as themselves and can change any of it.

## Consequences
- Changes made in Hermes persist across starts, Pikkumies updates and Hermes updates. That includes display, MCP servers, a web search backend and its key, fallback providers, memory, TTS and terminal settings, toolsets, plugins, checkpoints, the curator and background review, extra skill directories, and keys added by a Hermes update migration.
- The privacy pins are stronger: a change is refused at the source instead of being reverted at the next start.
- A normal start runs no extra process: one file read decides that nothing needs editing.
- New failure mode: a user `config.yaml` that no longer parses stays broken. Hermes then refuses non-interactive runs (one-shot prompts, nested agents) and falls back to its last good copy for interactive ones. Doctor and [the docs](../commands.md#changing-hermes-settings) name the copies to restore from.
- `/etc/hermes` is not read while `HERMES_MANAGED_DIR` is set (Hermes takes one managed directory); doctor says so when it exists.
- A bare `hermes` started with `HERMES_HOME` alone (not by Pikkumies) has no provider key, and its pins come from the seed only. Hermes' `save_config` removes managed keys from the user's file, so after such a save they are gone from the seed too. `cli.expose_on_path: false` keeps such a launcher off `PATH` ([ADR-0033](0033-vanilla-hermes-git-checkout-updated-separately.md)).
- Downgrading to a version from before this ADR rewrites both files again, which loses changes made after the upgrade. The backups from the move keep the state at the upgrade.
- A user's own Hermes hook on an event Pikkumies also hooks is replaced, since the managed list wins whole; local hook units ([ADR-0054](0054-tool-hooks-and-local-hooks.md)) are the way to add one.
- Someone who removes the generated directory from `skills.external_dirs` gets it back at the next start; `tools.disabled` and `skills.disabled` are the supported off switches.
- Not verified on a live host in this change (live QA was not run): that `hermes config set display.skin x` survives a restart, that `approvals.mode off` is refused, that the managed `.env` key reaches the provider, that a one-shot run with broken YAML shows Hermes' message, and that `pikkumies -m` overrides the pinned model.
