# ADR-0095: Software RAID is built, recovered and tuned through one tool; raw disk commands are refused

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-20
- Status: Accepted. Narrows [ADR-0073](0073-no-questions-no-deferrals-one-reviewed-exception.md)'s "formatting stays refused" by one exception; widens [ADR-0020](0020-deletes-need-the-users-approval.md)'s refusals. The number is a placeholder until it is merged.

## Context
The operator asked on 2026-10-20 for "the MD RAID building stuff, tools and skills to build, maintain, and manage MD RAID ... and the basic performance settings for big data or small data needs": tools, skills, prompts, doctrine, hooks and gates, whatever is needed.

What was there:
- The guard refused `mkfs` (only the literal word followed by `.` or a space), `wipefs`, `parted`, `sgdisk` and raw `dd` to a device, so Pikkumies could not build an array, but `mke2fs`, `mkswap`, `blkdiscard`, `cryptsetup luksFormat`, `pvcreate`, every `mdadm` mode and every `fsck` repair ran unasked. A test written first showed `mke2fs -t ext4 /dev/sdb1` and `mdadm --zero-superblock /dev/sdb` getting through.
- No unit read `/proc/mdstat` beyond the performance tool's "is a check running".
- Software RAID mistakes destroy data in a few known ways: an array "recovered" with `--create` (often `--assume-clean`) over a member that had been stale for months, then `fsck -y`; a re-add on a failed RAID5 that rewrote a member's role to spare; a scrub on a degraded array that wedged writes; a disk called empty because `blkid` found no signature, with data deeper in; `--create` without updating mdadm.conf, so the array came back under another number after a reboot.
- Linux 6.12.13 and its backports moved md bitmap accounting into `raid5_bitmap_sector()`, which rounded with `round_down()`/`round_up()`. Those need a power of two; with 3, 5, 6 or 7 data disks the marked range misses the write, so a re-add or a crash resync can skip it. Fixed upstream by 17ea021ae749 "md/raid5: round bitmap stripes with sector division". `drivers/md/raid5.c` at kernel.org stable tags, read on 2026-10-20: none before 6.6.79, 6.12.13 and 6.13.2; the mask in 6.6.79-6.6.156, 6.12.13-6.12.109, 6.13.2 to 6.17, 6.18.0-6.18.51, 6.19, 7.0, 7.1 and 7.2.0-7.2.5; the fix from 6.6.157, 6.12.110, 6.18.52, 7.2.6 and 7.3.

## Options Considered
- **Raw mdadm and mkfs behind the ask review (approve).** The review sees words, not devices: it cannot tell whether `/dev/sdc` is the blank disk or the stale member, and kernel names change between boots. Rejected.
- **A skill only, raw commands allowed.** The same failures, now with instructions. Rejected.
- **ZFS, LVM or btrfs RAID as well.** More surface; the common-mistakes list already warns against ZFS and double parity for random writes. Out of scope.
- **One tool that reads the live state just before it writes, raw commands refused** (chosen).

## Decision
- **Tool unit `tools/server-admin/mdraid/`** (PHP 7.3, `Cli::run`, JSON Lines). Verbs: `status`, `disks` (read), `create`, `add`, `replace` (`deletes`), `re-add`, `assemble`, `check`, `idle`, `tune` (`yes`). In `server-admin`, so `root.disabled` hides it; every verb but `status` needs root.
- **Root, uid 0 or sudo** (operator directive 2026-10-20: "make sure all 'only with sudo' also detects if running as root -- same thing, just no sudo needed"). The tool asks `Detect::rootAccess(posix_geteuid())` once per run, the check behind `root.available` ([ADR-0004](0004-provider-key-and-root-detection.md)), and keeps no sudo probe of its own. `uid0`: every program runs directly, files are read and written in PHP. `sudo`: every program runs as `sudo -n <program>` (never a password prompt); a root file is written by copying a private 0600 temp file with `sudo -n cp`, a directory made with `sudo -n mkdir -p -m 0700`, a disk sample read with `sudo -n dd`, a file only root can read with `sudo -n cat`; the tool's PHP, which lives in the account's home, is never run as root. `none`: every privileged verb is refused with the reason (not uid 0 and no passwordless sudo, or uid 0 without full capabilities). The agent runs `php mdraid.php`, never `sudo php`.
- **Formatting is allowed inside this tool only, after its own device check.** That is the one exception to ADR-0073's refusal; the raw-terminal refusals get wider. `create` re-runs the disk preflight in its own process, saves each disk's `--examine`, wipes only disks named in `--destroy`, runs `mdadm --create` (metadata 1.2, internal bitmap on redundant levels, `--run` only after its own preflight), `mkfs.ext4 -n` then mkfs with stride and stripe_width, appends only this array's `--detail --brief` line to mdadm.conf (refused when its UUID or name is there; `--scan` would copy foreign arrays), runs `update-initramfs -u` and reads it all back. A failed step stops and says what was done before it.
- **The device check.** Disks by `/dev/disk/by-id` name or serial, never `sdX`; every device path a program gets is `/dev/mdN` or a live by-id entry at that moment. In use (mounted, swap, fstab, crypttab, held by md or dm, superblock in mdadm.conf) is never taken. Holds data (partitions, a signature from `blkid -p` or `wipefs -n`, an md superblock, a non-zero byte in sampled reads at fixed offsets, reported as counts only) needs its serial in `--destroy`, and the refusal names what was found. RAID0 needs `--no-redundancy`; mixed sizes losing more than 1% need `--accept-size-loss`; RAID6 is not offered.
- **The ask.** `--destroy` is added to guard-destructive's tool-convention marker (with `--with-data` and `--expect`), so a line with it is a `delete` question for the ask policy: it runs when the user's words cover it, else `BLOCK_CONFIRM`, and `BLOCK_UNCHECKED` where no yes can be checked. `create` on blank disks, and the recovery verbs, are not asked: they destroy nothing that has a copy nowhere else, and the tool's own refusals stand.
- **Recovery** follows the members' superblocks: `assemble` is always `--readonly` at first and takes the group at the newest Events (Events, Update Time, Role compared); one stale member is left out; two or more behind, too few to run, or two members claiming one role is refused; `--force` only after a plain assemble failed and only with every member in that group; `--writable` switches an assembled read-only array to read-write. `re-add` only on a running, degraded, not failed array, only into the member's own vacant slot, and refused on RAID4/5/6 with an internal bitmap and a non-power-of-two data-disk count unless the running kernel is known fixed (an unknown kernel counts as not fixed). `check` is refused on a degraded or busy array. Every write verb saves every member's `--examine` under `/var/lib/pikkumies-mdraid/` (root, 0700) first. The tool never passes `--assume-clean`, `--write-zeroes`, `--grow`, `--build`, `--update` or a repair action to mdadm.
- **Profiles** (`big-file`, `typical`, `small-file`) are data in `MdPlan.php` with their source in the file and in the unit README: chunk, stripe_cache_size, md read-ahead, mkfs options and mount options, each labelled as Pulsed Media's measured fleet value or as a default. The stripe cache is a floor the kernel pre-allocates (value x members x 4 KiB); `big-file` takes 32768 only while every parity array's pinned cache stays under 5% of RAM. `tune` writes them into one oneshot unit, `/etc/systemd/system/pikkumies-mdraid-tune.service` (`/bin/sh -c 'echo <int> > /sys/block/mdN/...'` lines only, built from validated names and integers; the unit never runs code from the account's home), applies them now and reads them back.
- **Guard** (`hooks/guard/guard-destructive/GuardDisk.php`, its own block): refused outright and named to the mdraid tool: mdadm read word by word (the mode found the way mdadm finds it; create, build, grow, incremental, zero-superblock, assume-clean, write-zeroes, every manage operation, `--force`, `--run`, `--update`, `--readwrite`, `--action` other than idle, and any option it cannot check, including an ambiguous prefix); `mke2fs`, `mkntfs`, `mkdosfs`, `mkexfatfs`, `mkreiserfs`, `mkudffs`; `cryptsetup luksFormat|erase`; `pvcreate`; `e2fsck`, `fsck`, `fsck.*`, `dosfsck` and `xfs_repair` without `-n`; writes into `/sys/block/mdN/md/` other than `check` and `idle` to `sync_action`, the scrub [ADR-0094](0094-drive-health-screen-verdict-and-grade-on-one-server.md) allows. Reads, `--stop`, `--readonly`, a plain `--assemble`, `--monitor`, `e2fsck -n` and `fsck -N` run. One owner per command, so the refusal names the right tool: raw drive writes and drive tooling (`badblocks -w`, `hdparm` writes, `blkdiscard`, `mkswap` on a device, NVMe and SCSI format or sanitize, output written onto a device, `repair` written to a `sync_action`) are ADR-0094's `GuardDrives.php`, checked first; mdadm syntax, `mdadm --action=repair` included, is this guard's.
- **Hook** `hooks/system/raid-degraded/` (pre_llm_call, failClosed false, 2 s): when the host cache says root is available, an array degraded, rebuilding or inactive in `/proc/mdstat` is named once per session per change, with `mdraid status` as the next step.
- **Security review (2026-10-20), folded in.** In use also covers: a disk whose md superblock (whole disk or partition) belongs to an array in `/proc/mdstat`, running or inactive, or is listed in `/etc/mdadm/mdadm.conf` or `/etc/mdadm.conf`; a disk whose array other disks still carry (`mdadm --examine --scan --verbose`) unless every one of them is destroyed in the same command; a disk open by a process (`/proc/<pid>/fd`), a btrfs device, a loop backing file. Just before anything is written to a selected disk the in-use check runs again, and a disk that holds data is wiped only after an exclusive open of it succeeded (`wipefs -a -n`, which opens O_RDWR|O_EXCL and writes nothing). Every write and its exit code is appended to `/var/lib/pikkumies-mdraid/actions.log` (0600). `tune` keeps only unit lines of its own exact shape. A kernel name without an upstream point release (`5.14.0-503.el9`, `6.8.0-45-generic` without `/proc/version_signature`) reads as unknown. With RAM unreadable, `big-file` takes the low stripe cache. The guard also refuses the mke2fs gap's siblings: sfdisk, cfdisk, gdisk, cgdisk, make-bcache, `bcachefs format`, `zpool create|labelclear`, a write to `/device/delete`, and md control writes through `/sys/dev/block/9:N` or a cd and a relative name; the md write rule is judged per part of a command, so a read in one part and a write elsewhere in another is no longer refused. The review's other siblings (`badblocks -w`, `nvme format|sanitize`, `hdparm --security-erase` and `--dco-restore`, `sg_format`, `sg_sanitize`, and any redirect, tee, cp, install, qemu-img or ddrescue onto a disk, a partition, an md, dm, mapper, loop or nbd device or a `/dev/disk/by-*` name) are refused by ADR-0094's drives guard, which was widened at the merge to cover those device names and copy tools. On PHP 7.3 a long mdadm option was read as empty (`substr` with a null length) and every long-option mdadm, reads included, was refused; fixed and tested on 7.3.
- **Doctrine**: an SOP, `doctrine/SOP/recover-a-degraded-or-failed-array.md`, and two common-mistakes entries, `recovery-is-assemble` and `no-signature-is-not-empty`.

## Consequences
- The agent can build and recover arrays on its owner's server without a raw command that could hit the wrong disk; a disk with data on it is destroyed only on a line the user's words cover.
- Raw `mdadm` writes, `mke2fs`, `blkdiscard`, `pvcreate` and fsck repair no longer run from the terminal even on a machine where they are safe; the message names the verb that does it. A read redirected out of an md control file (`cat .../md/x > f`) is caught by the write rule too.
- `check` is `yes`, not `loads`: a scrub on the owner's own array loads only that array, and the ask policy drops `load` anyway, so the outcome is the same without a mis-worded question.
- The kernel table is a snapshot of 2026-10-20; a stable release after it in an affected series reads as "fixed" only when it is past the listed end. Re-check the table when a new series appears.
- Boot or root arrays, reshape, superblock surgery, `repair`, arrays on partitions for the write verbs, RAID6, ZFS, LVM, btrfs, the OS scrub timers, mdmonitor mail setup and non-Debian write verbs are out of scope.
- Not verified live: no run on real or virtual disks yet. Before this is relied on, a throwaway VM with virtual disks should degrade, re-add and replace a member, and create, reboot and `status` an array with the tune values applied (the plan's phase 2 and 3 checks).
