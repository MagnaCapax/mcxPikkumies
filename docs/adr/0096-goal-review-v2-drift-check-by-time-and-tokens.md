# ADR-0096: The goal review checks for drift by time and tokens spent, over all of the user's requests, with 0-1000 scores

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-20
- Status: Proposed. Supersedes [ADR-0071](0071-goal-review.md)'s cadence, window, question set and `rounds`; keeps its defence (fixed answers in, fixed text out), its ledger and its log. Amends [ADR-0067](0067-interval-hook-units.md): under the launcher, interval spools and state are keyed by run and depth, not by session id.

## Context
The operator asked on 2026-10-20 for a check that the agent has not drifted from what the user asked. It runs first after at least 5 minutes and 75k tokens, then at most every 30 minutes and only after 600k more tokens. It sees every user message whole, the tool calls and the latest agent actions, within 30k tokens, where only the transcript is cut, from its start. It scores the work from 0 to 1000 with the cheapest model, asks whether memory and outside sources were checked when likely needed, and for an undecipherable request tells the agent to re-read it adversarially. Reminders only: no block.

ADR-0071 reviewed every ten minutes, over 8 requests of 1000 characters, and skipped the first turn. Nothing counted a session's tokens: `hooks/trace/session-context` keeps only the last request's context, per tmux pane ([ADR-0061](0061-status-line-memories-context-tool-calls-code-lines.md)). Hermes gives a session a new id at a compression (agent/conversation_compression.py), so a spool keyed by session id restarts there. A skill turn reaches `pre_llm_call` as Hermes' scaffold, with the user's instruction after the skill body (agent/skill_commands.py), and the 4000-character cut dropped it. The spool shed user records like any other once full.

## Options Considered
- **A second hook unit.** Rejected: it would duplicate goal-review's decision and add a third light-model caller to a shared rate limit.
- **Find the session lineage from `/proc` (the Hermes process as parent).** Rejected: more code and more guesses than one key the launcher controls.
- **Key counts by session id.** Kept only as the fallback without the launcher: it restarts at every compression, the long sessions this check is for.
- **The model writes the reminder.** Rejected, as in ADR-0071.
- **Break the 30k cap when the requests alone exceed it.** Rejected: whole requests are left out (never R1 or the newest three) and the gap is marked.
- **Hold the next tool call to deliver mid-turn.** Rejected: the operator asked for no blocks, and Hermes gives shell hooks no other mid-turn channel.

## Decision
- **Run key.** An interactive start (`bin/pikkumies`, the TTY session block) makes `PIKKUMIES_RUN = bin2hex(random_bytes(8))`, exports it before Hermes starts, and zeroes `local/state/session-counters/run-<key>.json` (`SessionCounters::resetRun`): `{"since", "tokens", "reqs", "asked"}`, integers only, 0600 in a 0700 directory, rewritten under `flock` LOCK_EX; readers may add integer keys of their own. Run files untouched for 7 days go at the next start. `runFile`, `resetRun`, `updateRun`, `readRun` are the contract.
- **Token counter.** `hooks/trace/session-context` (post_api_request) adds, for every request, a delegated agent's too, `tokens` (`usage.total_tokens` when an integer from 0 to 10 000 000, else `prompt_tokens` + `output_tokens`) and `reqs` 1. Without a valid key, or for a key no start zeroed, it writes nothing; the pane figures are unchanged.
- **Spool continuity** (`lib/HookRunCount.php`). The spool hash is `sha1('run:<key>:<PIKKUMIES_DEPTH>:<Hermes pid>:<its start time>')` under the launcher, else the sha1 of the session id. Hermes runs hooks without a shell, so the orchestrator's parent is the Hermes process, read from `/proc` (its pid and start time; without `/proc`, run and depth only). A compression keeps the process, so spool, cursor, unit state and pending notes carry over, for every interval unit; a `hermes` the agent starts from its terminal inherits the key and the depth but is another process, so its prompts never count as the user's. A delegated agent in the same process shares the spool; its turn records carry `subagent` and are never requests, and no pending note or hold is handed to it: Hermes names the platform at `pre_llm_call`, `post_llm_call` and `post_api_request` but not at `pre_tool_call`, so a session seen as `subagent` is remembered (`state/async/subagent/`, pruned with the rest). The run file is `PIKKUMIES_RUN`'s for every spool of the run. Without the launcher (the desktop app, a gateway) a spool's own run file is derived from its hash, `HookFeed` adds the tokens there, and the count restarts at a compression. `PIKKUMIES_RUN` is guarded like `PIKKUMIES_DEPTH`: the nested-agent guard stops the agent setting or unsetting it ([ADR-0020](0020-deletes-need-the-users-approval.md)).
- **Lookups**, counted as they happen into the run file (`memory`, `memoryAt`, `outside`, `outsideAt`), so spool shedding never loses one: memory = the memory tool's `search`, the kb or wiki tool, a read or search under `memory/`, `session_search`; outside = `web_search`, `web_extract`, `x_search`, a browser tool, `delegate_task`, `skill_view` of deep-research, the browse tool, `curl`/`wget` of a web address, or the user's deep-research skill turn.
- **Spool.** 1 MiB; shed tool records first, then agent texts together with the user rows that are not the user's (a delegated agent's prompt, a row Hermes added), the user's own requests last, never the newest. A user record keeps 12 000 bytes, cut at a whole character (a longer one gets `cut: <bytes>`), so four kept requests are at most about 16k estimated tokens whatever the script; a skill turn is stored as the user's instruction (or `/name`), the skill name and the first 600 characters of its body, extracted before the cut. Counter files are never written through a symlink.
- **Timing.** hook.md `every: 120` (the poll), `wake: reply`, `timeout: 100`. The unit answers `{"skip": true}` until due: the first review when `now - since >= 300` and `tokens >= 75000`; later ones when `now - lastReviewAt >= 1800` and `tokens - tokensAtLastReview >= 600000` (both kept in the unit's state, per spool). A call with no usable answer is tried again after 600, 1200, then 1800 s, without moving the token mark; after three in a row it counts as a review and waits for the regular gates. The ledger also refuses a goal-review call within 600 s of the account's last one (`HookLedger::spend` gap), so killed runs or many sessions cannot call faster; that skip looks again at the next answer. The call's timeout is what is left of 90 s, at most 80. Settings `hooks.goalReview.{firstAfter,firstTokens,thenEvery,thenTokens,model}`, the person's. The first turn is reviewed. `rounds` is retired.
- **Window** (`lib/GoalReviewWindow.php`, `lib/GoalReviewPrompt.php`). Never more than 30 000 estimated tokens (bytes / 3), the system text included: every request whole, short ones too, with the end of the agent text before a request of under 12 words; the skills invoked; the offered tools and pages (ADR-0071's candidates, dropped first when tight); then from the newest back the tool calls one line each and the start of the agent texts, merged oldest first with a line where each request arrived (10 estimated tokens kept for each). Requests left out are counted in a marker; at most 999 are shown, numbered R1..Rk, and the answer's numbers are mapped back to the requests' own. If the kept requests still do not fit, the longest is cut and marked `[cut for the 30k cap]`, and a last pass drops the oldest activity lines until the prompt fits. Between two lines carrying a fresh random marker, removed from the data.
- **One call**, 500 tokens out: 13 named lines in any order (GOAL, thrown away unread; CURRENT; CLEAR, ONTASK, MEMORY, OUTSIDE as 0-1000 or x; OPEN, WAITING, TOOLS, PAGES, KIND, GUESSED, CHAT). Strict parse: anything else, or an id not offered, discards the reply whole; scores clamp to 1000; x is unknown. ADR-0071's "changes data" question is dropped (the change check covers it, [ADR-0070](0070-mutation-check.md)).
- **Out.** A fixed header with the four numbers and the two lookup counts, then fixed sentences: drifting (ONTASK under 400 after at least 10 tool calls since the current request; under 650 otherwise the milder one), unclear (CLEAR under 300: re-read word by word, list the readings, work from the best-supported one, name it, say what only the user can settle; under 550: say which reading), memory (MEMORY 600 or more and no memory search since the current request; left out when the memory category is off), outside sources (OUTSIDE 650 or more and no lookup since it; the deep-research skill named only when research is on), ADR-0071's open, waiting, guessed, tool, page, checklist-kind and first-review checklist lines, "On track by this check" when none fired, and "These are prompts to double-check, not orders" when any did. At most 4000 characters, as `context` only; CHAT yes gives no note. Quotes: the current request, R1 and the open ones, keyed by their number.
- **Model.** `hooks.goalReview.model`, else `hooks.model` (its setting text says so), else the cheapest (30 input to 0.5 output) of the light ids named `<main>-...` and the light model llm.json already holds for the main model, in the rates the credits line cached (no new request), leaving out ids that name a non-chat use (embed, tts, transcribe, realtime, search, image, audio) and rates that are not whole numbers of 0 or more; else the light model.
- **Log** (`local/logs/goal-review/`): outcome, raw scores, current request, sentences fired, estimated input, requests shown and left out, the gates, the model, and after a note the follow-through (lookups made since, the next on-task score). Never a text. Daily cap 24, as before.

## Consequences
- Cost: at most 30k estimated tokens in and 500 out per review, at most 24 reviews a day per account by default and never two within 600 s (about 732k input tokens a day at most), against about 103k for ADR-0071. A provider with no light model pays main-model rates, bounded by the same cap.
- The poll answers skip until due, so one short worker run follows each finished answer; it reads the spool and makes no model call.
- Notes reach the agent at the user's next message, not mid-turn.
- Every agent of one interactive start counts into one file and keeps one spool per depth across compactions. A nested agent at another depth shares the run's tokens and lookups, so its own first review can come early. Without the launcher, counts and spools restart at a compression.
- Measured, not assumed: the log keeps scores and follow-through; the byte-per-token estimate can be checked against the endpoint's usage figures.
