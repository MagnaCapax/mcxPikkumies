# ADR-0099: Backup safety layer: status cache, snap, a backup check before deletes, pre-edit copies, no /dev/null on cron lines

## Metadata
- Author: Aleksi Ursin / MCX (with Väinämöinen)
- Date: 2026-10-20
- Status: Proposed. Placeholder number; the integration renumbers it. Adds the tool unit `backup/backup-safety`, the hook unit `guard/pre-edit-copy` ([ADR-0030](0030-hooks-as-units-run-by-one-orchestrator.md)), a check inside `guard/guard-destructive` ([ADR-0020](0020-deletes-need-the-users-approval.md)), two documentation sources and the verb `backup remote check`, and changes `backup remote passphrase` ([ADR-0049](0049-backup-remote-over-ssh.md)) and the cron-tick line ([ADR-0025](0025-scheduled-jobs-per-minute-tick-under-no-new-privs.md)).

## Context
The operator asked on 2026-10-20: detect at launch whether systematic backups are being made, cached separately so the hooks have the latest information; when a change could destroy data (`apt-get remove` and `rm` do, `apt-get install` and `echo x >> config` do not) and no backup method is known, take extra care: copy the specific files to `~/backups/` (or `/backups` with full system management) and suggest the user set up backups, pointing at the storage box page, where zero-knowledge end-to-end encrypted backups are cheap and quick to set up; when backups exist, make sure they work and are fresh (checked again when not checked within 7 days); no cron line hides its errors in /dev/null; before something very dangerous, check the backups and show the user a table of the 10 latest (where, size, name); before mutating a small config file, keep a local copy in a tmp folder no other user can touch; tools and skills to set up GPG end-to-end backups and to get the user to keep the key. Root counts the same as sudo (Detect::rootAccess: uid 0 directly, or passwordless `sudo -n`).

What was found:
- `tools/backup/{restic,borg,remote}` already list, size (borg `info`, remote `list` bytes, restic 0.17+ snapshot summaries), check and schedule. `backup remote` is a complete GPG-symmetric end-to-end pipeline, and the user is told to keep its key elsewhere, but `--confirm-saved` only recorded a promise.
- Nothing detected whether any backup exists, and no hook knew. The delete guard asked about `rm` but had no rule for package removal. No hook copied a file before an edit; `HermesConfigBackup` does it only for Pikkumies' own Hermes config.
- The per-minute cron-tick line was the one Pikkumies cron line that sent its output to /dev/null.
- A hook's approve message must fit `HookUnits::APPROVE_SHOWN` (350 characters), and the ask policy shows the agent only a fixed text (ADR-0073), so a 10-row table cannot travel in the question.
- Pikkumies cited no storage box address; the operator's agent verified `https://pulsedmedia.com/storage-boxes.php` and the wiki guide on 2026-10-20.

## Options Considered
- **A new backup engine or scheduler.** Rejected: the three units already do it; this layer only reads and copies.
- **Hooks that run the backup tools themselves.** Rejected: a repository check takes minutes and the network; hooks read a cache instead, refreshed in the background.
- **Ask the user before every `rm` without backups.** Rejected (ADR-0073): the agent is held once and told to copy first; the existing question still comes.
- **The 10-latest table inside the delete question.** Does not fit 350 characters; the question carries only "Latest backup: age, size, kind" when it fits, and the table goes to the agent in a hold-once block with the instruction to show it to the user.
- **A storage box address in code.** Rejected: one source of truth, `config/documentationSources.md`, read by name.

## Decision
- **Status cache** (`lib/BackupStatus.php`): `local/state/backup-status.json` (0600) holds every method found (restic, borg, backup remote, and other tools named on a crontab line or by a known config file; the system crontabs and /etc config files count only with root), each judged: working (latest at most 48 h old or twice its schedule, verified within 7 days, not empty, within 50 % of the size of the one before), broken, stale, unknown (another tool, or not verified in 7 days), and the whole state: working if any method works, else broken, stale, unknown, or none. No cache is unknown and is treated like none. restic and borg get a metadata `check` when their last one is over 7 days old; backup remote counts as verified only through its new `check` verb (the newest meta archive, else the newest full one of at most 10 GiB, streamed `get | gpg -d | pigz -d | tar -t | wc -l`, nothing written, only the entry count kept, every stage's exit code and error text), run again when the last is over 7 days old. A run whose byte count matched proves the upload, not that the archive decrypts. With only full archives over 10 GiB it stays unknown.
- **Refresh**: an interactive start refreshes it in the background when it is older than a day (`nohup flock -n ... timeout 120 ... status --refresh`, output in `local/logs/backup-status/last.log`), and says one line when the state is not working.
- **`backup-safety status [--refresh] [--latest N]`**: methods, the N latest backups across methods, a markdown `table`, the storage box and guide addresses, a suggestion when not working, and a `custody` line while the remote key is unconfirmed.
- **`backup-safety snap <path>... | --package <name>`**: `cp -a --reflink=auto` to `~/backups/<UTC>/` (relative paths kept), or `/backups/<UTC>/` for a path outside the home with root (uid 0 runs cp itself, sudo runs it through `sudo -n`); without root a path outside the home is copied into `~/backups` as far as the account can read it. Folders 0700 before anything is copied, files owner-only, base folders that are a symlink or another account's refused. Cap min(2 GiB, half the free quota or disk); over it nothing is copied and the user is pointed at real backups. `--package` copies the package's conffiles (dpkg-query) and needs root or sudo. Logged to `local/logs/backup-snap/YYYYMMDD.jsonl`; sources recorded for the guard.
- **Delete guard**: `apt`, `apt-get`, `aptitude` `remove|purge|autoremove|autopurge` and `dpkg -r|-P` become a delete question. Before any delete question the check (`GuardBackup.php`, reading only the cache) holds the agent once: a plain removal (rm, unlink, shred, truncate, `: >`, package removal) without a working backup is told to snap first, with the exact command and the storage box suggestion; a dangerous one (`rm -r`, package removal, every other delete rule) is told to show the user the 10-latest table first. The identical command in the same session within 30 minutes, or a removal whose targets were all snapped in the last 30 minutes, goes on to the question. Files only in /tmp, /var/tmp or /dev/shm (outside the home) need no copy. No session id: no hold. An append, an install or a copy is never held.
- **Pre-edit copies** (`hooks/guard/pre-edit-copy/`): before write_file, patch, `sed -i`, a `>` redirect or `truncate` rewrites an existing regular file of at most 1 MiB owned by the account (as uid 0 any owner; under `sudo sed -i` / `sudo truncate` another owner's file through `sudo -n cat`: root and sudo are the same rule), a copy to `local/tmp/pre-edit/<session>/<full path>`, a tmp folder under the account's quota (`lib/LocalTmp.php`: folders 0700 of this account checked with lstat, never through a symlink; files 0600 written as `.part` with `x` and renamed only when whole, from the opened handle checked by device and inode). At most 50 MB per session, one note per session saying where, one note when the folder cannot be trusted; session folders older than 7 days removed. Silent and fail-open. Not the shared /tmp: there another account could squat the folder or fill the root filesystem (CWE review 2026-10-20).
- **Cron lines**: no cron line Pikkumies writes sends output to /dev/null; the tick line writes `local/cron-tick.last` (in local/ itself: a missing redirect folder would stop the tick); the interval hook worker writes `local/logs/hook-async.last`, an existing old tick line is replaced at the next start, and a test scans every generated line.
- **Key custody**: `passphrase` shows the key in 12 groups of 4 with where to keep it (a password manager or paper, not this server, not the backup machine); `passphrase --confirm-saved` has the user type the saved copy back at their own terminal with echo off (spaces ignored) and compares it locally; only a match records `passphrase_saved_by_user` with the sha256 of the passphrase file, and a different file later (regenerated) counts as unconfirmed again. While unconfirmed, the start, the status and the 10-latest table carry one custody line: if this server is lost, the archives cannot be decrypted. It never feeds the verdict or the delete guard: a delete leaves the key on this server, so the backups still restore. The key stays on this host and with the user, never on the storage box.
- **Temporary files** of backup remote (stage stderr, small outputs) go to the same private `local/tmp`, never the shared /tmp; a receiver answer is read through a pipe and cut at 1 MiB. `check` and `restore` pass `--status-fd 2` to gpg and require `DECRYPTION_OKAY`: plain `--decrypt` also prints an unencrypted OpenPGP message and exits 0, so a backup machine could otherwise hand over content of its own.
- **Homes and root**: `HomePath::home()` uses `$HOME` only when this uid owns it, else the passwd entry, so `sudo -E` never makes root act in another account's folder; as uid 0 `snap` always copies into `/backups`. A snap that did not read back whole does not count for the delete guard, and a copy that grew past the cap is reported (`over_cap`).
- **Links**: `pm-storage-boxes` and `pm-zero-knowledge-backups` in `config/documentationSources.md` (type link, scope pmss), read by name on every host by the suggestion.

## Consequences
- An agent without a working backup copies what it is about to delete first, a dangerous delete shows the user what backups exist, a bad edit of a small file can be undone, and the user hears where cheap encrypted backups come from.
- One extra hold per removal command per session while no backup works; once a backup works, plain removals are not held.
- Trade-offs: the size-deviation rule flags a home that legitimately grew or shrank by half (stated as the reason, so the user can judge); third-party tools count as unknown; systemd timers are not read; a copy in `~/backups` counts against the quota and is not a backup; the pre-edit copies live in /tmp and go with a reboot.
